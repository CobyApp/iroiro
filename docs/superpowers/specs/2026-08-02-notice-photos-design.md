# 공지사항 사진 첨부 설계

- **작성**: 2026-08-02 · **상태**: 설계 확정(구현 전)
- **관련 문서**: [community-design](./2026-07-19-community-design.md)(공지 도메인 원 설계) · [image-path-strategy](../../image-path-strategy.md)(R2 키 규칙) · [r2-adoption](../../r2-adoption.md)(버킷·토큰 운영) · [data-modeling](../../architecture/data-modeling.md)(스키마 규칙)

## 배경·목표

공지사항은 텍스트 전용으로 설계됐다(본문 plain text 렌더 — XSS 표면 최소화). 이벤트 안내·이용법처럼 이미지가 필요한 공지가 생겨, **본문 아래 첨부 사진**을 추가한다. 본문 렌더 방식(plain text)은 바꾸지 않는다.

저장소에는 성격이 다른 사진 파이프라인이 둘 있다:

| | 상품 (admin 전용) | 게시판 (UGC) |
|---|---|---|
| 버킷 | 공개 — URL 직서빙, CDN 캐시 | 비공개 — 15분 서명 GET |
| 검증 | MIME·크기 사전 검사만 (admin 신뢰) | 4단계 체인 + ETag 조건부 복사 |
| 방어 | `requireAdmin` | rate limit · 만료 장부 · 신고 연동 |

공지는 **admin만 작성 + 전체 공개** 콘텐츠라 상품 파이프라인과 성격이 일치한다 → 상품 파이프라인을 확장한다. UGC 파이프라인(검증 체인·pending 장부·서명 서빙)은 익명 사용자 방어 장치라 도입하지 않는다.

## 확정 결정

1. **표시 형태 — 본문 아래 첨부**. 본문은 지금처럼 plain text, 사진은 본문 아래 순서대로 나열. rich text·본문 중간 삽입은 도입하지 않는다(XSS 표면 유지).
2. **저장·서빙 — 공개 버킷 공유, 직서빙**. 상품 공개 버킷(`R2_BUCKET`)에 `notices/original/{uuidv7}.{ext}` 키로 저장, `R2_PUBLIC_BASE` URL로 직접 서빙(CDN 캐시 가능). `original/` 세그먼트는 image-path-strategy의 변형(variants) 자리 예약 규칙을 따른 것.
3. **포맷 — JPG·PNG·WebP 3종, HEIC 거부**. 상품은 HEIC를 허용하지만 공지는 공개 `<img>`로 직서빙되므로 브라우저에서 표시되지 않는 HEIC를 클라이언트에서 거부한다(의도적 차이). iOS는 게시판과 동일하게 재인코딩 경로가 우회로가 된다.
4. **수량·크기 — 최대 10장, 파일당 5MB**(상품과 동일 수치, 상수는 notices 도메인 소유). 합계 상한은 두지 않는다(admin 신뢰).
5. **순서 — 배열 순서가 곧 순서**. 클라이언트는 r2Key 배열만 보내고 서버가 배열 index를 `display_order`로 부여한다. 순서 숫자를 받지 않아 중복·결번 검증이 필요 없다.
6. **수정 — 전체 교체**. 저장 시 최종 키 목록으로 `deleteMany` + `createMany`(상품 update 동형). 유지할 사진은 r2Key를 재제출한다.
7. **삭제·고아 — 방치 수용**. 공지 soft delete 시 `notice_photo` 행과 R2 객체를 모두 유지한다(원래 전체 공개였던 콘텐츠·admin 소량). 업로드 후 저장하지 않은 고아 객체, 교체로 제거된 객체도 방치한다. 필요해지면 `notices/` prefix 정리 잡을 후속으로 도입한다.
8. **클라이언트 유틸 승격 — `lib/photo-client.ts`**. 게시판의 재사용 가능한 클라이언트 로직(HEIC 판정·`reencodeToBlob`·`putWithRetry`·허용 3종/클라 치수 상한/업로드 타임아웃 상수)을 lib로 승격하고 posts는 import 경로만 바꾼다(동작 불변). 공지가 `modules/posts`를 직접 import하면 아키텍처 룰 1(도메인 간 직접 의존 금지) 위반이라 승격이 선행 조건이다. posts 전용 로직(개수·합계 상한, pendingPhotoId 와이어링, `preparePhotos` 오케스트레이션)은 posts에 남는다.

## 데이터 모델 — `notice_photo`

`init_notice.sql`에 in-place 추가(pre-launch 관례) 후 `db:reset`. Prisma `NoticePhoto` 모델 추가 + `db:generate`.

```sql
CREATE TABLE notice_photo
(
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    notice_id     BIGINT      NOT NULL,
    r2_key        TEXT        NOT NULL,
    display_order INT         NOT NULL DEFAULT 0,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX notice_photo_notice_id_idx ON notice_photo (notice_id, display_order);
CREATE UNIQUE INDEX notice_photo_r2_key_unique ON notice_photo (r2_key);
CREATE INDEX notice_photo_created_at_idx ON notice_photo (created_at);

COMMENT ON TABLE notice_photo IS '공지 첨부 사진';
COMMENT ON COLUMN notice_photo.id IS 'PK';
COMMENT ON COLUMN notice_photo.notice_id IS '공지 ID';
COMMENT ON COLUMN notice_photo.r2_key IS 'R2 객체 키';
COMMENT ON COLUMN notice_photo.display_order IS '표시 순서';
COMMENT ON COLUMN notice_photo.created_at IS '생성일';

-- ============================================================================
-- GRANT — app 롤만(Data API 미노출).
--   - notice       : DELETE 미부여(soft delete 강제)
--   - notice_photo : 전체 교체(delete+insert) 패턴이라 행 불변 → UPDATE 미부여
-- ============================================================================
REVOKE ALL ON notice, notice_photo FROM anon, authenticated, app;
GRANT SELECT, INSERT, UPDATE ON notice TO app;
GRANT SELECT, INSERT, DELETE ON notice_photo TO app;
```

- **`updated_at` 없음**: 전체 교체 패턴이라 행이 불변(append-only) — data-modeling.md "불변 테이블은 `created_at`만" 규칙과 order_item 선례를 따른다. 같은 이유로 UPDATE GRANT도 부여하지 않는다.
- `product_photo` 대비 제외 컬럼: `is_thumbnail`(목록 썸네일 없음) · `alt_text`(YAGNI) · `created_by`/`updated_by`(notice 본체가 admin 스탬프 보유).
- FK 없음 규칙에 따라 `notice_id`는 수동 인덱스 — `(notice_id, display_order)` 복합으로 두어 상세 조회의 `WHERE notice_id = ? ORDER BY display_order` 패턴을 인덱스만으로 커버한다(§조회·렌더). 참조 무결성은 앱 트랜잭션이 보장한다.

## 업로드 플로우 (admin)

상품과 동일한 "첨부 즉시 업로드 → 저장 시 키 목록 기록" 2단계.

```
[NoticeForm 안의 NoticePhotoUploader (신규 컴포넌트, modules/notices/components/)]
  파일 선택
    → lib/photo-client: HEIC 거부 · 3종 MIME 검사 · 4096px 리사이즈 재인코딩
    → presignNoticePhotos([{filename, mimeType, sizeBytes}]) 호출
    → 발급된 uploadUrl로 PUT (putWithRetry) · r2Key 로컬 보관 · 미리보기 표시
[저장(생성/수정)]
  createNotice / updateNotice 입력에 photos: string[] (r2Key 배열) 포함
    → tx 안에서 notice 저장 + (수정이면 deleteMany 후) createMany
       display_order = 배열 index
```

**`presignNoticePhotos` 액션** (`modules/notices/actions.ts`):

- `requireAdmin()` → 장수(1~10)·MIME(3종)·크기(5MB) 검사 → 파일별 `buildNoticeR2Key(filename)` = `notices/original/{uuidv7()}.{ext}` (`lib/r2/presign.ts`에 상품 `buildR2Key` 옆에 추가) → `getSignedUploadUrl`로 presign PUT 발급
- 반환: `{ r2Key, uploadUrl }[]` (상품 `presignProductPhotos` 동형)

**스키마 변경** (`modules/notices/lib/schema.ts`):

```ts
export const NOTICE_PHOTO_MAX_COUNT = 10;
export const NOTICE_PHOTO_MAX_FILE_BYTES = 5 * 1024 * 1024;

const photosSchema = z
  .array(z.string().regex(/^notices\/original\/[^/]+$/, "잘못된 사진 키입니다"))
  .max(NOTICE_PHOTO_MAX_COUNT, `사진은 최대 ${NOTICE_PHOTO_MAX_COUNT}장까지 첨부할 수 있습니다`);

// noticeCreateSchema — 생성은 빈 상태에서 시작하므로 생략 = 사진 없음으로 안전하다
photos: photosSchema.default([]),

// noticeUpdateSchema — 수정은 전체 교체(결정 6)라 생략이 곧 전체 삭제다. 기본값을
// 두지 않아 호출부가 의도를 명시하게 강제한다(생략 시 타입 에러로 잡힌다)
photos: photosSchema,
```

prefix 정규식은 경로 오입력(타 도메인 키·경로 탈출)을 데이터 경계에서 차단한다. **update에만 기본값이 없는 것은 실수가 아니다** — 수정은 전체 교체라 `photos`를 생략하면 해당 공지의 사진이 전부 삭제된다. 일관성을 이유로 두 스키마를 다시 통일하지 말 것.

## 조회·렌더

- **대상 조회 2곳**: 공개 상세 `getNoticeByPublicCode`와 admin 수정 폼 `getNoticeById`에 `notice_photo`를 `display_order` 순으로 포함한다. 목록 계열(`listNotices`·`listHomeNotices`)은 변경 없음(YAGNI) — `Notice` DTO의 `photos`는 목록에서 빈 배열.
- **DTO**: `photos: { r2Key: string; url: string }[]` 단일 형태. `url = getPublicUrl(r2Key)`. admin 수정 폼이 전체 교체 재제출에 r2Key를 필요로 하고, 공개 URL 자체가 `{base}/{key}` 조합이라 키 노출은 추가 정보가 아니다.
- **공개 상세 렌더**: 본문(`whitespace-pre-wrap`) 아래 `<img>` 나열(`max-width: 100%`). width/height 미저장이라 로드 시 레이아웃 이동(CLS)이 있을 수 있으나 수용(YAGNI — 필요 시 후속에서 치수 저장).
- **admin 수정 폼**: 기존 사진을 미리보기로 표시, 개별 제거·추가 후 저장 시 최종 목록 제출.

## 에러 처리

| 상황 | 처리 |
|---|---|
| HEIC·미지원 포맷 선택 | 클라이언트에서 즉시 거부 — 게시판과 동일 문구 "지원하지 않는 이미지 형식입니다 (JPG·PNG·WebP만 가능)" |
| presign 실패 (비admin·검증 실패) | `ActionResult` 오류 — 업로더가 항목별 실패 표시 |
| PUT 업로드 실패 | `putWithRetry` 재시도 후 실패 항목만 제외, 나머지로 저장 가능 |
| 저장(생성/수정) 실패 | 업로드된 객체는 방치(결정 7) — 재시도 시 새 presign |
| 잘못된 r2Key 제출 | zod prefix 정규식이 거부 |

## 보안

- **유일한 가드는 `requireAdmin`이다.** presign·저장 모두 admin 세션 실검증 뒤에만 통과한다.
- presign은 `Content-Type`·`Content-Length` **어느 것도 서명에 고정하지 않는다** — `getSignedUploadUrl`이 `allHeaders` 없이 서명해 aws4fetch가 둘 다 `UNSIGNABLE_HEADERS`로 제외하며, 실제 서명 범위는 `SignedHeaders=host`다.
- 따라서 MIME·크기 검사는 **presign 시점의 자기신고 값 검증**이며 업로드된 객체에 강제되지 않는다. 서버 실측 검증(HEAD·매직바이트·픽셀)도 하지 않는다.
- 이 전제가 성립하는 근거는 이 경로에 **`requireAdmin`으로 admin만 도달 가능**하다는 것이다.
- 대조: UGC 경로(`lib/r2/ugc.ts`)는 `allHeaders: true`로 실제로 헤더를 고정한다.
- 공유 헬퍼 `getSignedUploadUrl`의 하드닝(서명 범위 확대)은 products·auth·banners·notices 4경로에 영향을 주고 실 R2 검증이 필요해 **별도 작업으로 분리**했다.
- 공개 버킷 직서빙이므로 서명·만료 개념이 없다. 삭제된 공지의 사진 URL이 계속 열리는 것은 결정 7의 수용 범위.

## 테스트 방침

기존 스타일(Prisma-mock 호출 인자 검증) 그대로. 통합 테스트는 추가하지 않는다(신규 동시성·잠금 없음 — test-policy 기준).

- `presignNoticePhotos`: 비admin 거부(re-throw) · 장수/MIME/크기 검증 · 반환 계약
- `createNotice`/`updateNotice`: photos 반영 — createMany 인자(배열 index = display_order), 수정 시 deleteMany 선행
- transform: `photos` DTO 매핑(`display_order` 순, `getPublicUrl` 조합)
- `lib/photo-client` 승격: 기존 posts 테스트가 경로 변경 후에도 통과(동작 불변 확인)

## 문서·설정 갱신

- **환경변수·버킷·토큰 변화 없음** — 기존 공개 버킷·`R2_PUBLIC_BASE` 사용.
- `R2_BUCKET` 설명이 "상품 공개 버킷"인 3곳(README env 표 · environment-variables.md · r2-adoption 버킷 용도 표)을 "공개 버킷(상품·공지)"로 갱신.
- community-design 스펙은 수정하지 않는다(공지 사진은 본 스펙이 단일 진실).

## 범위 밖 (후속 후보)

- `notices/` prefix 고아 객체 정리 잡
- 사진 치수 저장(CLS 개선) · 변형(variants) 생성
- 공지 목록 썸네일 노출
- 본문 중간 이미지 삽입(rich text) — 도입 시 XSS 방어 재설계 필요
