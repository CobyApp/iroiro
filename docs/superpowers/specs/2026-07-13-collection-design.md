## 요약

유저가 이 샵에서 **구매한 포토카드**를 SUKISUKI(카와라보 토레카) 같은 **공개 그리드 컬렉션**으로
자랑·공유할 수 있는 화면을 추가한다. 구매(결제완료)는 **보유 원장**(`inventory_item`)에만 자동
기록되고(웹훅 재전송에도 **멱등**), 유저가 **컬렉션을 직접 만들어 보유 항목을 등록**하면 그때
전시된다(`collection` / `collection_item`). 공개 URL `/collections/{public_code}` 로 비로그인
방문자도 볼 수 있고, **공개 읽기 경로는 주문·결제·PII 테이블을 일절 건드리지 않는다.**

## 배경 · 목표

- **레퍼런스**: `SUKISUKIトレカ for KAWAII LAB.`(Asobisystem, 공식 디지털 트레카 컬렉션 서비스).
  `/users/{code}` 공개 마이페이지의 **룩앤필**(멤버/그룹별 그리드, 공유 URL)을 차용한다.
  단 레퍼런스는 *디지털 가챠* 서비스이고 본 프로젝트는 *실물 포토카드 리셀*이라,
  **레어리티·가챠·수집률(컴플리트) 메카닉은 도입하지 않는다.**
- **핵심 목적**: **자랑·공유(소셜)**. 유저가 자기 컬렉션을 공개 URL로 남에게 보여준다.
- **범위**: 이 샵에서 **구매한 카드만**(결제완료 주문에서 도출). 외부에서 산 카드의 수기 추가는 범위 밖(→ 후속).
- **비목표(MVP 제외)**: 레어리티/시리즈/세트, 수집률, 유저간 트레이드, 커스텀 핸들, 외부 카드 수기, 부분환불.

## 핵심 설계 결정 (와 근거)

### 1. 공개 식별자 = 별도 `public_code` (내부 PK/`account.id` 미노출)

- **형식**: base62 12자, **암호학적 RNG(CSPRNG)**, `UNIQUE` 제약 + 충돌 시 재생성.
- **`account.id`(UUIDv7)를 직접 노출하지 않는 이유**:
  - UUIDv7은 앞 48비트가 생성 시각 → URL만으로 **가입시각이 밀리초까지 유출**된다(RFC 9562).
  - PK라 **회전·폐기 불가**(공유 링크 리셋/비공개 전환 불가).
  - `order.account_id`·세션·RLS(`app.current_account_id`)의 축이라 **내부 신원과 공개 신원이 결합**된다.
  - `order_no`를 PK와 분리한 것과 동일 원칙(내부 키 ≠ 외부 키).
- **표준 패턴 근거**: "내부 PK + 공개용 별도 랜덤 식별자"는 웹 표준(Stripe `cus_…`, YouTube 11자 랜덤,
  Rails `friendly_id`/`prefixed_ids`, Django `public_id`). ULID/UUIDv7은 **시각 유출**이라 공개용 부적합.
- **중복 방지 = 길이가 아니라 `UNIQUE` + 재시도**로 보장한다. 기존 `runWithUniqueCodeGuard`(주문번호 채번의
  23505 재시도 가드)를 재사용한다. base62 12자 공간 ≈ 3.2×10²¹ 이라 실 규모(수만~수백만)에서 충돌은 사실상 0.
- **형식은 앱(zod)/생성기가 검증**하고, DB는 "외부 식별자로 말이 안 되는 값" 방지용 **느슨한 sanity CHECK**만 둔다
  (선례 `order_no`도 형식 CHECK 없음 → 일관성. strict regex는 향후 prefix/길이 변경 시 마이그레이션 마찰).

### 2. 보유(자동) ↔ 전시(수동) 분리 — 2026-07-17 전환

- **`inventory_item`(보유 원장, 자동)** — 주문 `paid` 시 `order_item` 단위 기여분 1행을 적재.
  `UNIQUE(order_item_id)`로 **멱등**(웹훅 재전송·재처리에도 중복 가산 없음). 환불 시 `reversed_at`
  스탬프. 표시 스냅샷(상품명·썸네일 등)을 원장에 저장해 보유 목록 화면이 자립한다.
  **공개 DTO에 절대 미포함.**
- **`collection_item`(전시 등록, 수동)** — 유저가 보유 상품을 컬렉션에 **등록**하는 **순수 관계**
  (`collection_id`+`product_id`+`sort_order`만, 2026-07-17 도출형 확정). 표시 데이터(이름·썸네일·
  수량·획득일)는 **조회 시 활성 원장에서 도출** — 재구매 증가·환불 감소가 자동 반영되고, 활성
  0이면 표시에서 제외(행은 유지 → 재구매 시 **자동 복원**). 저장 정합·락 기계가 불필요해진다.
- **결정적 이유**: (a) 전시는 **의도적 공개** — 프라이버시 우선 기조와 정합(NBA Top Shot의
  collection/showcase 구조와 동형). (b) 공개 읽기 경로가 `order`·`payment`·`account` 등 주문·PII
  테이블을 **아예 접근하지 않게** 유지(원장은 집계·스냅샷만 조인, `order_item_id` 등 원시 필드
  비선택) → "구매가·주문 내역 비노출"을 아키텍처 수준에서 보장.
- **원장을 두는 이유(Codex 리뷰 반영)**: 집계 행만 두면 (a) 웹훅 재전송 시 중복 가산, (b) 환불 시 과차감,
  (c) 감사 불가. 원장이 멱등 키·정확한 역산·이력을 제공한다(프로젝트의 `order_status_history` append-only 철학과 동류).

### 3. 가벼운 큐레이션

- 큐레이션 = **등록/해제**(넣기 모델). 별도 숨김 플래그 없음 — 빼고 싶으면 해제한다.
- 카드 **자유 배치**(`sort_order`, 2026-07-17 — `is_pinned` 이진 고정을 대체: 대표 고정 = 앞 순번 배치.
  실물 바인더 배치 문화와 정합, 컬렉션 재배치와 동일 UI/규칙). 컬렉션 전체 **공개 토글**(`is_public`,
  **기본 비공개** = 프라이버시 우선, opt-in 공개).

### 4. 3테이블 구조

`inventory_item`(비공개 보유 원장, 결제 시 자동 적재) → *유저 등록* → `collection_item`(전시 등록 관계, 표시 데이터는 조회 시 원장 도출) ⊂ `collection`(유저 생성 앨범, 회원당 N개).
역할 직교: **원장 = 사실(무엇을 얼마나 보유)** · **컬렉션 = 전시 공간** · **컬렉션 항목 = 전시 선택(+배치 순서)**.

## 데이터 모델

신규 마이그레이션 `supabase/migrations/<YYYYMMDDHHMMSS>_init_collection.sql` (파일명 타임스탬프는 구현 시 채번).
컨벤션 준수: 단수 테이블명 · `BIGINT IDENTITY` PK · **FK 미사용**(`*_id` + 수동 인덱스) · 스냅샷 ·
`CREATE TABLE → ALTER ADD CONSTRAINT → CREATE INDEX → COMMENT` 블록 · 파일 끝 GRANT/RLS · 모든 테이블/컬럼 한국어 COMMENT.

### collection — 컬렉션(유저 생성 전시 앨범)

```sql
CREATE TABLE collection
(
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    account_id  UUID        NOT NULL,
    public_code TEXT        NOT NULL,
    title       TEXT        NOT NULL,
    is_public   BOOLEAN     NOT NULL DEFAULT FALSE,
    sort_order  INT         NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE collection
    ADD CONSTRAINT collection_public_code_sane CHECK (length(btrim(public_code)) BETWEEN 8 AND 64);
ALTER TABLE collection
    ADD CONSTRAINT collection_sort_order_positive CHECK (sort_order > 0);

CREATE UNIQUE INDEX collection_public_code_unique     ON collection (public_code);
CREATE INDEX        collection_account_sort_order_idx ON collection (account_id, sort_order);
CREATE INDEX        collection_created_at_idx          ON collection (created_at);
CREATE INDEX        collection_updated_at_idx          ON collection (updated_at);
```

- **`title`가 필요한 이유**: `account`는 RLS로 "본인만 SELECT"라 공개 페이지에서 **타인의 `display_name`을
  읽을 수 없다.** 공개 표시명을 `collection`에 두어야 공개 읽기가 `account`를 건드리지 않고 자립한다.
  생성 시 소유자의 `display_name`으로 시드하고, **최초 공개 전 유저가 확인/수정**한다(§프라이버시).
- **다중 컬렉션·유저 생성(2026-07-17)**: 회원당 컬렉션 N개 — **유저가 직접 생성·삭제**한다
  (1개 제한이 필요하면 화면/앱 정책으로). 보유/전시 분리 전환으로 "구매 적재 대상(기본 컬렉션)"
  개념은 소멸 — 자동 생성 경로가 없어 생성 동시성 장치(ensureDefaultCollection)도 불필요해졌다.
  - `sort_order`는 **순수 노출 순번**(`ORDER BY sort_order, id`). 유니크를 일절 두지 않는다
    (재배치 시 non-deferrable unique의 일시 위반 고통 회피 — `display_order` 선례와 동일 운영).
    중복·간극은 무해하며 앱이 정리한다. 생성 시 `MAX+1`(첫 컬렉션은 1) 부여.
  - 삭제 시 등록 항목(`collection_item`)도 같은 tx에서 함께 삭제한다(FK 없음 — 앱 cascade).
- `UNIQUE(public_code)` = 공개 코드 유일성(생성 시 code 충돌 P2002는 재생성 재시도로 회복).
- `collection_public_code_sane` = 형식이 아니라 "빈 값/비상식 길이" 방지용 백스톱(형식은 앱).

### collection_item — 컬렉션 항목(전시 등록 관계, 도출형)

```sql
CREATE TABLE collection_item
(
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    collection_id BIGINT      NOT NULL,
    product_id    BIGINT      NOT NULL,
    sort_order    INT         NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE collection_item
    ADD CONSTRAINT collection_item_sort_order_positive CHECK (sort_order > 0);

CREATE UNIQUE INDEX collection_item_collection_product_unique ON collection_item (collection_id, product_id);
CREATE INDEX        collection_item_collection_sort_order_idx ON collection_item (collection_id, sort_order);
CREATE INDEX        collection_item_product_idx    ON collection_item (product_id);
CREATE INDEX        collection_item_created_at_idx ON collection_item (created_at);
CREATE INDEX        collection_item_updated_at_idx ON collection_item (updated_at);
```

- **순수 등록 관계(2026-07-17 도출형 확정)** — 등록 시 생성(유저 액션, `sort_order = 컬렉션 내
  MAX+1`), 해제 시 삭제. `sort_order`는 원장에서 도출 불가능한 유일한 상태(이 컬렉션에서의 전시
  순서)라 관계에 남는다 — 유니크 없음(`collection.sort_order`·`display_order` 선례와 동일 운영,
  동순위는 `id`). 스냅샷·수량·획득일 캐시를 두지 않으므로 **저장 정합·advisory lock 기계가 전부 불필요**하다.
- **표시 데이터는 조회 시 원장 도출**: `(collection.account_id, product_id)`별 활성 원장 집계 —
  `quantity = SUM`, `acquired_at = MIN`, 스냅샷은 최신 활성 행 기준. 재구매·환불이 자동 반영된다.
- **활성 합계 0인 등록은 표시에서 제외**(행은 유지) — 재구매하면 자동 복원된다. 등록 검증(활성
  보유 > 0)은 UX용이며, 동시 환불과의 경합은 도출이 자가 치유하므로 락이 필요 없다.
- **행 참조(`inventory_item_id`)를 두지 않는 이유**: 원장 행은 획득 이벤트 단위라 특정 행 참조는
  부분 환불·재구매에서 죽은 참조가 된다. 두 테이블은 `product_id` 축으로만 만난다.
- **dedup 단위 = `product`(판매 상품/상태포함 SKU) 단위**이지 추상적 "같은 카드"가 아니다. 동일 포토카드를
  다른 `condition`으로 사면 서로 다른 `product` → 서로 다른 행. *canonical 카드 병합은 카드 카탈로그가 없어 범위 밖.*
- `collection_id` 조회는 복합 유니크의 선두 컬럼이 커버 → 별도 단일 인덱스 불필요.

### inventory_item — 보유 원장(멱등·역산·감사, 비공개)

```sql
CREATE TABLE inventory_item
(
    id                    BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    account_id            UUID        NOT NULL,
    product_id            BIGINT      NOT NULL,
    order_item_id         BIGINT      NOT NULL,
    product_name          TEXT        NOT NULL,
    product_thumbnail_key TEXT,
    item_type             TEXT        NOT NULL,
    team_id               BIGINT,
    member_id             BIGINT,
    quantity              INT         NOT NULL,
    acquired_at           TIMESTAMPTZ NOT NULL,
    reversed_at           TIMESTAMPTZ,
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE inventory_item
    ADD CONSTRAINT inventory_item_quantity_positive CHECK (quantity > 0);

CREATE UNIQUE INDEX inventory_item_order_item_unique   ON inventory_item (order_item_id);
CREATE INDEX        inventory_item_account_product_idx ON inventory_item (account_id, product_id);
CREATE INDEX        inventory_item_created_at_idx      ON inventory_item (created_at);
CREATE INDEX        inventory_item_updated_at_idx      ON inventory_item (updated_at);
```

- **테이블명 결정(2026-07-17)**: 실사용 관례 조사(Steam Inventory·PlayFab/Unity Economy·RPG 스키마의
  player/character_inventory) 후 `inventory_item` 채택. 판매 재고는 `product.stock`(`stock.ts`)이므로
  "inventory = 회원 보유"로 읽는다(혼동 주의는 COMMENT로 완화).
- **`UNIQUE(order_item_id)`** = `paid` 재처리(웹훅 재전송) 멱등의 핵심. 재적재는 skipDuplicates.
- **주문 데이터 도출이 아닌 별도 원장 유지(2026-07-17 확정)**: `order_item`(+`order.status`)로도
  보유를 도출할 수는 있으나 채택하지 않는다 — (a) 도출은 `status IN (...)` allowlist 결합이라
  `shipped`/`delivered` 전이 도입 시 보유 카드가 조용히 사라지는 사고 경로가 생긴다. 원장은
  전이 이벤트 계약(paid에 적재, 환불에 역산)이라 상태 어휘 확장과 무관. (b) 수기 등록(후속 #2)의
  확장점. 원장은 단방향 파생(주문 tx 내 원자 append, 멱등)이며 `order_item`×상태와 대사로
  상호 검증 가능(후속 #8) — 상류 기록 + 도메인 원장 + 대사 구조(Stripe Ledger 동형).
- **계정 스코프(`account_id`)** — 컬렉션과 독립적으로 존재(컬렉션 0개여도 보유는 기록된다).
  등록 항목 정합은 `(account_id, product_id)` 활성 합계로 계산.
- **스냅샷을 원장에 저장** — 보유 목록(인벤토리 피커)이 `product`/`order` 조인 없이 자립하고,
  상품 삭제·수정에도 표시가 유지된다. 등록 시 `collection_item` 스냅샷의 원천이기도 하다.
- **`reversed_at`** = 환불/취소 시 스탬프. **부분환불은 MVP 미지원**(`order_item` 단위 전체 reverse).
  부분환불 요구가 생기면 `reversed_quantity INT` 또는 별도 reversal 원장으로 확장(→ 후속).
- 원장은 **DELETE 하지 않는다**(감사 보존). 삭제되는 건 등록(`collection_item`)뿐.

### GRANT / RLS

```sql
REVOKE ALL ON inventory_item, collection, collection_item FROM anon, authenticated, app;
GRANT SELECT, INSERT, UPDATE         ON inventory_item  TO app;
GRANT SELECT, INSERT, UPDATE, DELETE ON collection      TO app;
GRANT SELECT, INSERT, UPDATE, DELETE ON collection_item TO app;
```

- **RLS**: 세 테이블 모두 **비-PII**라 `order`/`cart_item` 선례대로 **RLS 미적용**, 인가는 **앱 DAL**이 담당:
  - 공개 read: `collection.is_public = true` 필터 + 원장 **집계·스냅샷 도출 조인**(2026-07-17 도출형
    전환 — `order_item_id` 등 원시 필드는 SELECT하지 않아 공개 DTO 미포함). 주문·PII 테이블은 미접근.
  - 소유자 관리(생성·삭제·등록·해제·고정·공개토글·title): `collection.account_id = current_account_id`로 스코프.
- `account_id`는 서버측에서만 사용하고 **공개 클라이언트로 절대 반환하지 않는다**(코드→회원 역매핑 차단).
- *defense-in-depth로 공개-read/owner RLS 정책 추가 여부는 `docs/architecture/rls-best-practices.md`에서 확정(후속).*

## 라이프사이클 (멱등·원자적)

- **컬렉션 생성/삭제(유저 액션)**: 유저가 직접 생성한다(자동 생성 없음). `title`은 소유자
  `display_name`으로 시드하고 최초 공개 전 확인/수정(§프라이버시). `sort_order = MAX+1`(첫 컬렉션 1).
  `public_code` 충돌(P2002)은 코드 재생성 재시도로 회복. 삭제 시 등록 항목도 같은 tx에서 삭제.
- **적재(주문 → `paid`)** — 승인 반영과 **같은 DB 트랜잭션 안에서**(F4):
  각 `order_item`마다 `inventory_item`에 createMany(skipDuplicates) — 멱등, `acquired_at = 결제 시각`,
  `quantity = order_item.quantity`, 스냅샷 포함. **이것으로 끝** — 컬렉션은 건드리지 않고(등록은
  유저 액션), 표시 수량은 조회 시 도출이라 저장 정합·락이 없다(2026-07-17 도출형 전환).
- **등록/해제(유저 액션)**: 등록 = 활성 보유 > 0 검증(UX용 — 동시 환불과의 경합은 도출이 자가 치유)
  후 `collection_item` 생성. 해제 = 행 삭제. `UNIQUE(collection_id, product_id)`가 중복 등록 차단(P2002).
- **정리(주문 → `canceled`/환불)** — 같은 트랜잭션:
  해당 주문의 `order_item` id 목록(orders 도메인이 도출·전달)으로 `inventory_item` 행에
  `reversed_at` 설정(전체 reverse) — 원장에 `order_id`는 없다(`order_item` 경유 도출, 2026-07-17 제거).
  **이것으로 끝** — 활성 0이 된 등록은 조회에서 제외되고(행 보존), 재구매 시 자동 복원된다.
- **통합 지점**: `paid`/`canceled` 전환은 `modules/orders`가 소유. 거기서 **tx client를 넘겨** `modules/collection`의
  적재/정리 함수를 호출한다(원자성). 대규모/비동기화가 필요해지면 outbox/repair job으로 승격(후속).

## 공개 읽기 경로 (격리 확인)

```
GET /collections/{public_code}      ← URL 단위는 컬렉션(회원 단위 공개 페이지는 후속 논의)
  → collection  WHERE public_code = ? AND is_public = true      (없으면 404 — 비공개·없는 코드 동일 응답)
  → collection_item  WHERE collection_id = ?                    (등록 관계 + sort_order)
  → inventory_item  집계 조인: (account_id, product_id)별 SUM(quantity)·MIN(acquired_at)
        + 최신 활성 행의 스냅샷(이름·썸네일·유형·팀·멤버). 활성 0인 등록은 제외.
        ※ order_item_id 등 원시 필드는 SELECT하지 않음(공개 DTO 미포함)
        정렬: sort_order ASC, id ASC (앱에서; 컬렉션당 소량)
  → member / team  (그룹핑 라벨용, 공개 카탈로그)
  ✗ order / order_item / payment / order_address / account  — 미접근(주문·PII 테이블)
```

## 프라이버시 · 보안

- 공개 페이지는 **카드 정체(이미지·이름·멤버·그룹)와 보유 매수만** 노출한다. **결제 금액·주문번호·결제수단·
  배송지·이메일·전화·`account_id`·원장(`order_item_id`)은 비노출.**
- `is_public` 기본 FALSE(opt-in). **최초 공개 전 `title` 확인/수정** 단계를 둔다 — `display_name`이 실명/외부
  닉네임일 수 있어 seeded title을 그대로 공개하지 않는다(F7).
- 비공개/존재하지 않는 `public_code`는 **동일하게 404**(존재 여부 노출 차단).
- `public_code`는 열거 불가(랜덤)이나, 이는 방어심화일 뿐 **실제 접근 제어는 `is_public` + 앱 인가**가 담당.

## 후속 작업 (범위 밖, 별도 사이클)

1. 커스텀 핸들(`/u/{handle}`) — 고유성·형식검증·예약어·사칭정책·변경 UX. `public_code`는 안정 fallback 유지.
2. 외부 구매 카드 수기 등록 — 주문에 연결되지 않는 보유 항목(`inventory_item` 모델 확장). *이게 열리면 아래 인덱스 승격 트리거.*
3. 레어리티/시리즈/세트·수집률 — 참조 서비스의 수집 메카닉(현재 스키마에 개념 없음, 대규모 신규).
4. canonical 카드 키 — 상태·로트 무관 "같은 카드" 병합. 도입 시 투영 dedup 키를 canonical key로 교체.
5. 부분환불 — **별도 reversal 행(contra entry) 방식 권장**(2026-07-17 원장 BP 조사 반영 — storno 원칙:
   정정은 행 수정이 아니라 반대 기입 추가, 부분환불 N회 이력도 자연 보존). `reversed_quantity` 컬럼은 차선.
6. **공개 조회 캐시 승격** — 공개 페이지가 고트래픽/바이럴이거나 원장 집계 조인이 실측 병목이면
   `collection_item`에 `quantity`/`acquired_at`/스냅샷 **캐시 컬럼 재도입**(+쓰기 시 정합 로직) 및
   전용 인덱스 추가. 외부 수기등록으로 컬렉션이 수천행+가 될 때도 재검토.
7. 메모/코멘트(풀 큐레이션), defense-in-depth RLS, 회원 단위 공개 페이지(공개 컬렉션 나열).
   *(진열 순서 자유 배치는 2026-07-17 `sort_order`로 본편 반영 — UI 재배치 액션만 구현 대상.)*
8. **원장 대사(reconciliation) 체크** — 원장 ≠ `order_item`×주문상태 드리프트를 찾는 검증 쿼리
   (관리자 화면 또는 크론). 원장 BP 조사(Stripe 대사 관행) 권고 사항.
   *(등록 항목 수량 대사는 도출형 전환으로 불필요해짐 — 저장된 수량 자체가 없다.)*

## 테스트 방침

`agent/rules/test-policy.md`를 따른다. 우선 순수 로직 단위 테스트 대상:
- `publicCode`: base62-12 생성(문자셋·길이·CSPRNG).
- `materialize` **멱등성**: 동일 `paid`(order_item) 재처리 시 원장 중복 미삽입, 스냅샷·수량 저장.
- `materialize` **역산**: `reversed_at` 스탬프(행 보존, 재실행 멱등), 지정 라인·계정 스코프만 영향.
- 도출 조회(queries, 구현 시 추가): 활성 합계·최초 획득일 계산, 활성 0 등록 제외, 타 계정 격리.
- 등록/해제 액션(구현 시 추가): 활성 보유 검증·중복 등록 차단(P2002).
- 공개 쿼리가 주문·PII 테이블을 참조하지 않고, 원장에선 집계·스냅샷만 선택함(격리) 검증.

전체 플로우(결제→적재→공개 렌더)는 실 DB + 결제 연동에서 수동 검증.
