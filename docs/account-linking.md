# 계정 연동·병합 설계

소셜 로그인(카카오·네이버)으로 **같은 사람이 여러 `account`를 만드는 문제**를, 전화 인증을 축으로 하나의 회원으로 합치는 설계.

**구현 상태**: ✅ deferred 가입(닉네임 필수 입력 후 account 생성, `display_name` NOT NULL) 완료 — `pending_account` 테이블(쿠키엔 무작위 토큰, 세션과 동일 패턴)·`/signup`·`completeSignupAction`. ⏳ 전화 인증 온보딩 + dedup/병합(아래 슬라이스 3~6)은 미구현.

> 관련 코드: `modules/auth/`. 스키마: `supabase/migrations/`의 `init_account`. 무FK 정책: [lessons/05](./lessons/05-foreign-keys.md). 세션: [lessons/13](./lessons/13-session-vs-jwt.md).

## 결정

1. **목표는 "한 검증된 사람 = 한 회원"** — 주문내역·장바구니를 로그인 수단(카카오/네이버/…)에 무관하게 한 계정으로 본다. 이건 이커머스 표준이며 옳은 end-state.
2. **그러나 "전화 인증되는 순간 조용히 자동 병합"은 하지 않는다.** 병합은 **OTP 성공 이후**에만 트리거하고, 사라질 계정에 **거래 데이터가 있으면 명시적 본인 확인(step-up)**을 거치며, 모든 병합은 **감사 기록 + 소프트(tombstone)**로 되돌릴 수 있게 한다.
3. **join 키는 "검증된 전화번호"로 시작**하되, 추후 본인확인(CI/DI) 도입 시 **CI를 안정 키로 승격**한다(전화번호는 변경·재사용되므로).
4. **신규 가입은 닉네임을 입력받은 뒤에야 account를 INSERT한다(deferred creation).** OAuth 콜백은 신규 신원이면 account를 만들지 않고, 검증된 신원을 짧은 수명 쿠키에 담아 가입 폼으로 보낸다. 닉네임 제출 시 account+identity+session을 원자 생성 → 그래서 `display_name`은 **NOT NULL**이며 null 닉네임 행이 존재하지 않는다. 닉네임은 **표시용(비유니크)** — 제공자 값 프리필·수정 가능·필수.

### 왜 (근거 — 다중 소스 검증)

- **조용한 자동 병합 = 계정 사전탈취(account pre-hijacking) 취약점.** USENIX Security 2022 / Microsoft MSRC 연구는 상위 75개 서비스 중 35개+가 *Classic-Federated Merge* 공격에 취약했고, **"휴대전화번호 등 다른 식별자로도 가능"**하다고 명시 — 전화 기반 자동 병합도 사정권.
- **벤더 합의는 만장일치**: Auth0/Okta("이메일로 자동 연동 금지, 항상 재인증"), Ory("임의 제공자 완전 자동 연동 미지원"), Clerk(검증된 이메일에만 + 미검증이면 비번 변경 강제), Google(조용히 병합 안 함, 기존 제공자 재로그인 요구). 공통분모: **검증된 식별자 + 양쪽 계정 통제 확인 후 연결.**
- **한국 특화**: 정석 dedup은 CI(사람당 교차서비스 연계값)/DI(사이트당 중복가입 방지값)(KISA). 단 카카오는 *"CI가 없을 수 있고, 한 사람이 인증 계정 최대 3개, 전화번호는 변함"*이라 **전화번호 문자열 단독을 영구 키로 쓰지 말라**고 경고.
- **OTP 게이팅이 강한 방어**: 공격자는 피해자 SIM이 없어 OTP를 통과 못 한다 → 악의적 병합 트리거 자체가 막힌다(검증된 전화 ≫ 미검증 이메일).

출처는 문서 하단 [참고](#참고) 참조.

## 상태 모델 — 가입(deferred creation) → 온보딩 → 병합

신규 가입은 **닉네임 입력 후에야 account가 생긴다.** 전화는 외부 의존(SMS 게이트웨이)이라 account 생성 후 온보딩 단계로 분리한다.

```
OAuth 콜백:
  identity 존재(재방문) → 로그인(세션 발급)                              ← 기존 사용자
  identity 신규        → account 안 만듦. 검증된 신원(provider·provider_user_id·email·제공자닉네임)을
                         pending-account 서명 쿠키(httpOnly·Secure·~10분)에 담아 /signup 으로 (비로그인)
/signup 제출(닉네임 필수):
  닉네임 검증 → account(display_name 포함) + identity + session 원자 생성 → 로그인
        ↓
온보딩: phone_number_verified_at IS NULL → /onboarding/phone (OTP) → dedup/병합(아래)
```

- 가입 직후 account = **"로그인됨 + 닉네임 있음 + 전화 미검증"**. `display_name`은 생성 시점부터 **NOT NULL**.
- dedup/병합은 **OTP 성공 이후에만** 일어난다.
- **닉네임**: 제공자 값 프리필 + 수정 가능 + **필수**(빈 값 제출 불가; 앱 검증 trim·min 1·max). **표시용 — 비유니크**(고유 핸들 필요 시 별도 `username` 분리 — [미해결·후속](#미해결--후속-구현-전-확정-필요) 참조).

## 스키마 (init_account in-place 편집 — pre-launch)

```sql
-- (a) account.display_name: deferred creation 으로 가입이 '닉네임 입력 후' INSERT 되므로 NOT NULL 강제
ALTER TABLE account ALTER COLUMN display_name SET NOT NULL;
--  ※ /signup 핸들러가 항상 닉네임을 넣는다(빈 값은 앱 검증으로 차단). 표시용이라 유니크는 두지 않음.

-- (b) account: tombstone 포인터 — 병합은 '삭제'가 아니라 '소프트 병합'(감사·복구 가능)
ALTER TABLE account ADD COLUMN merged_into_account_id UUID;   -- 흡수돼 사라진 계정 → 생존 계정
ALTER TABLE account ADD COLUMN merged_at TIMESTAMPTZ;
--  ※ 병합 시 흡수된 계정의 phone_number_verified_at 을 NULL 로 비워야
--    account_phone_number_verified_uq(1전화=1계정) 부분 UNIQUE 제약과 충돌하지 않는다.

-- (c) 연동/병합 감사 테이블 — 무FK(앱 레이어 무결성), CHECK 가드
CREATE TABLE account_link_audit (
    id                   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    surviving_account_id UUID        NOT NULL,
    merged_account_id    UUID,                 -- 'identity 추가' 링크면 NULL(사라진 계정 없음)
    event                TEXT        NOT NULL,  -- 'link_identity' | 'merge_account'
    trigger              TEXT        NOT NULL,  -- 'phone_onboarding' | 'settings_link' | 'admin'
    moved_identity       TEXT,                  -- 'kakao:382...' (provider:provider_user_id)
    step_up              TEXT        NOT NULL DEFAULT 'none', -- 'none'|'phone_otp'|'reauth_provider'
    detail               JSONB,                 -- 이동 카운트/스냅샷 {identities,sessions,orders,...}
    actor_account_id     UUID,                  -- 개시자(본인/어드민)
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT account_link_audit_event_chk   CHECK (event   IN ('link_identity','merge_account')),
    CONSTRAINT account_link_audit_trigger_chk CHECK (trigger IN ('phone_onboarding','settings_link','admin'))
);
CREATE INDEX account_link_audit_surviving_idx ON account_link_audit (surviving_account_id, created_at DESC);
```

OTP 저장소는 전화 인증 온보딩을 구현하는 시점에 별도 추가한다.

## 핵심 결정 로직 (OTP 검증 후)

```
verifyPhoneOtp(currentAccountId, phone, code):
  OTP 검증(구현 시 추가될 단기 저장소의 해시·시도횟수·만료·사용 여부) 실패 → { failed }

  existing = account WHERE phone_number = phone
                      AND phone_number_verified_at IS NOT NULL
                      AND id != currentAccountId
                      AND merged_into_account_id IS NULL

  ── 없음 → current 에 전화 확정. { verified }
            UPDATE current SET phone_number=phone, phone_number_verified_at=now()

  ── 있음 → existing 이 '정본', current(방금 OAuth)가 흡수 대상
       hasValuableData = existing 에 주문/결제/포인트 존재?   (현재는 항상 false → 주문계 생기면 true)
       ├─ false → 투명 병합: mergeAccounts(surviving=existing, merged=current, stepUp='phone_otp')
       │           → { linked, survivingAccountId }   (세션 재지정, 즉시 완료)
       └─ true  → 즉시 병합 금지. { merge_confirm_required, existingAccountId, summary }
```

> **왜 `existing` 데이터 유무로 분기하나**: OTP는 *지금 전화 통제*를 증명하지만, 한국 번호 재사용(recycling) 때문에 *과거 그 계정 주인과 동일인*까지는 보장 못 한다. 그래서 **잃을 게 있는 계정(existing에 주문)**일 때만 step-up으로 막는다.

## 함수 시그니처 (modules/auth — 아키텍처 룰 2 준수: Server Actions는 `actions.ts`)

```ts
// modules/auth/lib/account.ts  (server-only) — deferred creation
export async function findAccountByIdentity(provider: OAuthProvider, providerUserId: string): Promise<Account | null>;
//   기존 findOrCreate 를 분리: 콜백은 '찾기'만. 신규면 account 없이 가입 폼으로.
export async function createAccountFromSignup(input: {
  provider: OAuthProvider; providerUserId: string; email: string | null;
  displayName: string;                 // 가입 폼에서 받은 닉네임(검증 통과, 항상 non-null)
}): Promise<Account>;                   // account + identity 원자 생성. 호출 후 createSession.

// modules/auth/lib/phone.ts  (server-only)
export async function requestPhoneOtp(accountId: string, phone: string): Promise<void>;

export type PhoneVerifyResult =
  | { status: "verified" }
  | { status: "linked"; survivingAccountId: string }
  | { status: "merge_confirm_required"; existingAccountId: string; summary: MergeSummary }
  | { status: "failed"; reason: "code_mismatch" | "expired" | "too_many_attempts" };

export async function verifyPhoneOtp(
  currentAccountId: string, phone: string, code: string,
): Promise<PhoneVerifyResult>;

// modules/auth/lib/link.ts  (server-only)
export type MergeSummary = { orders: number; points: number; carts: number; identities: number };

export async function linkIdentityToAccount(tx: Tx, identityId: bigint, targetAccountId: string): Promise<void>;

export async function mergeAccounts(opts: {
  survivingAccountId: string;
  mergedAccountId: string;
  trigger: "phone_onboarding" | "settings_link" | "admin";
  stepUp: "phone_otp" | "reauth_provider" | "none";
  actorAccountId: string;
}): Promise<{ survivingAccountId: string; moved: MergeSummary }>;

// modules/auth/actions.ts  (Server Actions — 세션 가드 포함)
export async function completeSignupAction(formData): Promise<ActionState>;   // pending-account 쿠키 검증 → createAccountFromSignup + 세션
export async function requestPhoneOtpAction(formData): Promise<ActionState>;
export async function verifyPhoneOtpAction(formData): Promise<ActionState>;   // → PhoneVerifyResult
export async function confirmMergeAction(formData): Promise<ActionState>;     // step-up 확인 후 mergeAccounts
export async function startProviderLinkAction(provider): Promise<void>;       // 설정: 제공자 추가 연결 시작
```

## `mergeAccounts` 트랜잭션

```ts
db.$transaction(async (tx) => {
  // 1) 두 계정 잠금·검증(FOR UPDATE): merged≠surviving, 둘 다 살아있음(merged_into NULL)
  // 2) 신원 이전:  UPDATE account_identity SET account_id=surviving WHERE account_id=merged
  //      └ UNIQUE(provider, provider_user_id)는 전역이라 충돌 없음(한 계정에 kakao 2개도 허용)
  // 3) 세션 재지정: UPDATE account_session SET account_id=surviving WHERE account_id=merged
  //      (보안 강화 옵션: merged의 잔여 세션 폐기)
  // 4) 도메인 데이터 ADDITIVE 이전 (확장 지점 — 주문계 생기면):
  //      orders/cart/points/coupons → account_id=surviving (포인트 합산, 쿠폰 union)  ※ 현재 no-op
  // 5) 프로필 보존: surviving 우선, surviving의 NULL 필드만 merged에서 백필
  // 6) tombstone: UPDATE merged SET merged_into_account_id=surviving, merged_at=now(),
  //               phone_number_verified_at=NULL   ← 전화 UNIQUE 충돌 방지(필수)
  // 7) 감사: INSERT account_link_audit(event='merge_account', trigger, step_up, moved_identity, detail, actor)
});
```

**하드 삭제 대신 tombstone** → 잘못된 병합도 추적·되돌림 가능(리서치의 "additive·auditable" 원칙).

## step-up 분기 (existing 에 데이터 있을 때)

```
verifyPhoneOtp → merge_confirm_required
        ↓ UI: "이미 이 번호로 가입된 계정이 있어요. 연결하면 기존 주문/포인트를 함께 보게 됩니다."
   ├─ 저가치(기본): [연결] = 명시적 동의 → confirmMergeAction(stepUp='phone_otp')
   └─ 고가치(주문/결제 큼): + "기존 가입에 쓰던 카카오/네이버로 다시 로그인" 요구
                            → 기존 제공자 재인증 성공 후 confirmMergeAction(stepUp='reauth_provider')
취소 → 병합 안 함(현재 계정 유지). 절대 자동 병합하지 않는다.
```

## 설정 화면 "제공자 추가 연결" (2차 플로우)

```
로그인 상태에서 [네이버 연결] → startProviderLinkAction('naver')  (OAuth start에 intent='link' 표식)
콜백(intent='link' && 로그인됨):
   ├─ 그 신원이 미사용 → linkIdentityToAccount(현재계정) + audit(event='link_identity')
   └─ 그 신원이 타 계정 소속 → 병합 상황 → merge_confirm 경로로
```

## 보안 가드레일 → 설계 매핑

| 리서치 요구 | 이 설계의 충족 |
|---|---|
| 검증된 식별자에만 연결 | 병합은 **OTP 성공 후에만** 트리거 |
| 양쪽 계정 통제 증명 | OTP=기존계정 전화키 증명, 고가치는 +기존 제공자 재인증 |
| 조용한 자동 병합 금지 | 데이터 있으면 **명시적 확인** 필수, 투명 병합은 빈 계정만 |
| pre-hijacking 방어 | 공격자는 피해자 SIM 없어 OTP 불가 → 트리거 차단 |
| additive·audit | tombstone + `account_link_audit` + 포인트 합산/동의 union |

## 엣지 케이스

- **번호 재사용**: 고가치 계정은 기존 제공자 재인증으로 차단. CI 도입 전 임시 방어.
- **한 사람 카카오 2계정**(카카오 경고): 한 계정에 kakao identity 2개 허용 → 병합돼도 무탈.
- **tombstone 세션 방어**: DAL `getCurrentAccount`가 `merged_into_account_id IS NOT NULL`이면 거부(또는 따라가기). 정상 경로는 세션을 옮기지만 방어적으로 처리.

## 미해결 · 후속 (구현 전 확정 필요)

- **닉네임 유니크 여부**: 현재 설계는 **표시용 비유니크**. 공개 핸들(프로필 URL·@멘션 등)이 필요해지면 `display_name`과 별개의 `username`(대소문자 무시 유니크·트림·예약어 차단)으로 분리 — 미결정.
- **PIPA 동의**: 두 신원의 개인·거래 데이터 결합에 별도 항목 동의가 필요한지 법률 확인. (리서치 미증명 — 변호사 확인)
- **거래 데이터 reconciliation**: 주문/결제/포인트/쿠폰이 양쪽에 있을 때의 충돌 해소·환불·PG 정산 규칙은 **표준 권위 소스가 없음** — 주문 도메인 생길 때 additive+audit 원칙으로 별도 설계.
- **CI 승격**: 본인확인 도입 시 join 키를 전화 → CI로 바꾸고 재검증 주기 정의.

## 구현 순서 (TDD)

1. 스키마(`display_name` NOT NULL + tombstone 컬럼 + `account_link_audit`) → `db:reset`
2. **deferred 가입**: `findOrCreateAccountByIdentity` → `findAccountByIdentity` + `createAccountFromSignup` 분리, 콜백을 '신규=가입 폼' 흐름으로, pending-account 쿠키, `/signup`(닉네임 프리필·필수) — **닉네임 검증·원자 생성 테스트**
3. `phone.ts`(OTP req/verify) — **순수 dedup 결정 로직 단위테스트**(verified/linked/confirm/failed 분기)
4. `link.ts`(`mergeAccounts` 트랜잭션) — **병합 불변식 테스트**(신원·세션 이전, tombstone, 전화제약, 감사행)
5. actions + `/onboarding/phone` UI
6. 설정 "제공자 연결"(2차)
