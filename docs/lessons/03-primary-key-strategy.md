# 03. Primary Key 전략

## 왜 알아야 하는가

PK 선택은 시스템 전체에 영향을 미칩니다 — URL 구조, 클라이언트 동작, 인덱스 효율, 분산 가능성, 보안까지 한 번에 결정됩니다. 한 번 정하면 되돌리기 어렵습니다.

## 두 후보

| 옵션 | 문법 | 비고 |
|---|---|---|
| **`BIGINT IDENTITY`** | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | SQL 표준, Postgres 10+ 권장. MySQL의 `AUTO_INCREMENT` 대응 |
| **`BIGSERIAL`** | `id BIGSERIAL PRIMARY KEY` | 옛날 스타일. 내부적으로 sequence + DEFAULT. IDENTITY로 갈아타는 추세 |
| **`UUID`** | `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` | `pgcrypto` extension 필요. 분산·클라이언트 발번 친화 |

`SERIAL` vs `IDENTITY`: 둘 다 자동 발번이지만 `IDENTITY`가 SQL 표준이고 더 깔끔. 새 프로젝트는 `IDENTITY` 권장.

`GENERATED ALWAYS` vs `BY DEFAULT`:
- `ALWAYS`: 수동 id 삽입 막음. 우회하려면 `OVERRIDING SYSTEM VALUE`
- `BY DEFAULT`: 평소 자동, 필요 시 수동 삽입 허용. 시드·dump/restore 친화적

## 비교 표

| 관점 | `BIGINT IDENTITY` | `UUID` |
|---|---|---|
| **PK 생성 위치** | DB가 INSERT 시점에 부여 | 어디서든 사전 생성 가능 |
| **분산 환경 충돌** | 샤딩·멀티 DB 합칠 때 위험 | 충돌 확률 ~0 |
| **URL 노출** | `/products/1` enumerable (총 개수 추정 가능) | `/products/9b1deb4d-...` 추측 불가 |
| **외부 시스템 매칭** | 매핑 테이블 필요 | ID 그대로 넘김 |
| **저장 크기** | 8 bytes | 16 bytes |
| **인덱스 지역성** | 시간순 INSERT가 끝에 몰려 캐시 친화적 | 랜덤이라 페이지 흩어짐 (쓰기 약간 느림) |
| **사람 가독성** | "12345번 상품" — 외우기 쉬움 | 인간이 못 외움 |
| **시간 순서 추론** | id로 가능 | 불가 (`UUIDv7`로 해결 가능) |

## 한국 이커머스 사례 (실제 URL)

| 사이트 | 패턴 | slug? |
|---|---|---|
| 쿠팡 | `coupang.com/vp/products/{numericId}?...` | ❌ |
| 네이버 스마트스토어 | `smartstore.naver.com/{shop}/products/{numericId}` | ❌ |
| 무신사 | `musinsa.com/products/{numericId}` | ❌ |
| 마켓컬리 | `kurly.com/goods/{numericId}` | ❌ |
| 29CM | `29cm.co.kr/products/{numericId}` | ❌ |

**한국 대형 이커머스 대부분이 숫자 id, slug 없음.** 한국어 상품명을 ASCII slug로 변환하는 일관성 룰이 까다롭고, 검색 트래픽이 네이버/구글 검색결과 → 페이지 진입이라 URL을 사람이 읽을 일이 적기 때문.

## `r2_key`는 PK와 독립적

흔한 오해: "R2에 올릴 때 product의 id가 필요하니까 UUID로 해야 한다."

사실 r2_key는 **R2 버킷 내에서만 unique하면 되는 문자열**이라, 클라이언트가 별도 토큰(UUIDv4, nanoid, 해시)을 만들어 쓰면 됩니다. PK가 IDENTITY든 UUID든 r2_key 생성 흐름은 동일.

```ts
// IDENTITY PK여도 흐름 동일
const photoKey = `photos/${crypto.randomUUID()}.jpg`;
await r2.put(photoKey, file);
await db.insert(productPhotos).values({ productId, r2Key: photoKey });
```

## 이 프로젝트의 결정

**모든 5개 테이블 PK를 `BIGINT GENERATED BY DEFAULT AS IDENTITY`로 통일.** 이유:

1. **한국 이커머스 통념과 일치** — 쿠팡·무신사형 패턴
2. **MVP·소규모 셀러 사이트** — 분산·샤딩 무관
3. **Supabase 단일 DB** — UUID의 분산 친화성 이점이 발생하지 않는 환경
4. **저장·인덱스 효율** — 8 bytes (UUID 16 bytes보다 절반)
5. **`BY DEFAULT`** 선택 — 시드 데이터 import, dump/restore 시 수동 id 삽입이 가능해야 운영 편함

URL enumeration 우려는 향후 필요 시 `slug` 컬럼 추가로 해결 ([09. URL Slug 전략](./09-url-slug-strategy.md) 참고).

## 트레이드오프

이 결정으로 *포기한 것*:
- 클라이언트가 INSERT 전 id를 미리 알 수 없음 → 일부 워크플로우는 `RETURNING id`로 한 단계 더
- `/products/1` 같은 enumerable URL → 나중에 `slug` 추가 시 해결

이 결정으로 *얻은 것*:
- 인덱스 효율 ↑
- 사람이 읽고 외울 수 있는 id ("상품 5번 어디 갔음?")
- 한국 이커머스 컨벤션과 일치
