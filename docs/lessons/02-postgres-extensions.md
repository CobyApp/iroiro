# 02. Postgres Extension

## 왜 알아야 하는가

Postgres는 코어를 작게 유지하고 부가 기능을 **떼었다 붙일 수 있는 모듈**로 분리해서 배포합니다. UUID 생성, 지리정보, 벡터 검색, 암호화 같은 기능들이 모두 extension으로 들어옵니다. 관리형 Postgres(AWS RDS 등)는 지원 목록에 있는 확장만 `CREATE EXTENSION`으로 켤 수 있게 노출합니다.

## 핵심 개념

extension 하나가 추가할 수 있는 것:

| 종류 | 예 |
|---|---|
| **함수** | `gen_random_uuid()`, `digest()` (pgcrypto) |
| **데이터 타입** | `geometry`, `geography` (postgis), `vector` (pgvector) |
| **연산자** | `<->` (벡터 거리), `%` (pg_trgm 유사도) |
| **인덱스 종류** | `GIST`, `GIN`, `ivfflat` 등 새 타입에 적용 |
| **시스템 뷰** | `pg_stat_statements` 뷰 |
| **백그라운드 워커** | `pg_cron` 같은 스케줄러 |

라이브러리 import보다 깊게 — **DB 엔진 동작 자체를 확장**합니다. 인덱스 종류·연산자까지 추가할 수 있다는 게 일반 라이브러리와의 결정적 차이.

## 문법

```sql
-- 활성화 (이미 깔려 있으면 통과)
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- 특정 스키마에 설치
CREATE EXTENSION pgcrypto SCHEMA extensions;

-- 비활성화 (의존 객체 있으면 CASCADE 필요)
DROP EXTENSION pgcrypto;
DROP EXTENSION pgcrypto CASCADE;
```

`CREATE EXTENSION`은 "이미 OS·클러스터에 *설치된* 확장을 *현재 DB에 등록*" 합니다. 외부에서 다운받지 않습니다. 패키지 자체는 OS 패키지(예: `apt install postgresql-contrib`)나 Postgres 빌드에 포함되어 있어야 합니다.

권한: 보통 `CREATE EXTENSION`은 superuser 또는 그에 준하는 권한 필요. RDS에서는 마스터 유저(`rds_superuser`)가 지원 목록 안의 확장을 켤 수 있고, "trusted" 확장(pgcrypto 등)은 `CREATE` 권한만 있는 DB 소유자도 켤 수 있다. 비특권 `app` 롤로는 불가 — 확장은 스키마 적용(소유자) 단계의 일이다.

## 자주 쓰는 확장

| 확장 | 용도 | RDS PostgreSQL 17 | 로컬 `postgres:17` 이미지 |
|---|---|---|---|
| `pgcrypto` | 해시·HMAC·대칭 암호화, `gen_random_uuid()`(PG13+는 코어에도 있음) | ✅ 지원 | ✅ contrib 포함 |
| `uuid-ossp` | UUID v1/v3/v5 (v4만 필요하면 코어 `gen_random_uuid()`로 충분) | ✅ | ✅ |
| `pg_trgm` | 유사어 검색, `LIKE`/`ILIKE` 가속 | ✅ | ✅ |
| `postgis` | 지리정보 (위치, 거리, 폴리곤) | ✅ | ❌ 별도 이미지(`postgis/postgis`) 필요 |
| `vector` (pgvector) | 임베딩 벡터 검색, 시맨틱 서치 | ✅ | ❌ 별도 이미지(`pgvector/pgvector`) 필요 |
| `pg_stat_statements` | 쿼리 통계 모니터링 | ✅ (기본 preload) | ✅ contrib 포함 |
| `pg_cron` | DB 안에서 스케줄 작업 | ✅ (파라미터 그룹에 preload 필요) | ❌ 별도 설치 |

로컬과 운영의 확장 가용성이 다를 수 있다 — 그래서 확장을 쓰기로 하면 **로컬 이미지부터 바꿔서 같은 `db/schema.sql`이 양쪽에서 돌게** 한다.

## 조회·관리

```sql
-- 이 DB에 켜진 확장 목록
SELECT extname, extversion FROM pg_extension;

-- 사용 가능한(설치되어 있지만 안 켜진) 확장 목록
SELECT * FROM pg_available_extensions WHERE installed_version IS NULL;

-- 특정 확장이 추가한 객체 보기
SELECT
    pg_describe_object(classid, objid, objsubid) AS object
FROM pg_depend
WHERE refobjid = (SELECT oid FROM pg_extension WHERE extname = 'pgcrypto')
  AND deptype = 'e';
```

## 관리형 Postgres(RDS) 컨텍스트

RDS는 확장을 미리 켜 주지 않는다 — 지원 목록 안의 확장을 **DB마다 `CREATE EXTENSION`으로 명시**해야 하고, 일부(`pg_cron`, `pg_stat_statements`)는 파라미터 그룹의 `shared_preload_libraries`에도 올려야 한다. 이 프로젝트에서 그 자리는 `db/schema.sql` 맨 앞이다 — 스키마 적용(`db-apply.sh` / `npm run db:reset`)이 곧 확장 활성화가 되도록.

확장을 스키마 파일에 명시하면 좋은 점:
- 다른 환경(로컬 `compose.yml` Postgres, GitHub Actions의 서비스 컨테이너, RDS dev/prd)에서 같은 `db/schema.sql`을 돌릴 때 안 깨짐
- 의존성이 코드에 명문화 — 뭘 쓰는지 한눈에 보임

명시 안 하면 어떤 환경에선 우연히 켜져 있어 동작하고 다른 환경에선 함수가 없다는 에러가 난다. 이력: 초기 Supabase는 `pgcrypto` 등을 기본 활성화해 뒀어서 이 함정이 잘 안 보였다.

## 이 프로젝트의 결정

현재 사용하는 확장 **없음** — `db/schema.sql`에 `CREATE EXTENSION`이 한 줄도 없다(2026-05-09 결정, 2026-09 기준 유지).

처음에는 `gen_random_uuid()`를 PK 디폴트로 쓰려고 `CREATE EXTENSION IF NOT EXISTS pgcrypto`를 넣었으나, 카탈로그 PK를 `BIGINT GENERATED BY DEFAULT AS IDENTITY`로 변경하면서 함께 제거했습니다 ([03. Primary Key 전략](./03-primary-key-strategy.md) 참고). 이후 회원 계열이 UUID PK를 쓰지만 **UUIDv7을 앱(`uuid` 패키지 `v7()`)에서 생성**해 넣으므로 DB 확장이 필요 없습니다. 확장 0개인 덕에 `postgres:17` 공식 이미지·RDS 어디서든 `db/schema.sql`이 그대로 돕니다.

향후 추가 가능성:
- **`pg_trgm`** — 상품명·그룹명 유사어 검색 (예: 오타 허용 검색)
- **`vector`** — 굿즈 이미지 임베딩 기반 시맨틱 검색
- **`postgis`** — 오프라인 매장 위치 검색 (해당 기능 추가 시)
