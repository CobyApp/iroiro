# 08. R2 스토리지 패턴

## 왜 알아야 하는가

이미지·동영상·파일 같은 **바이너리는 DB가 아니라 객체 스토리지**에 두는 게 정석입니다. DB에 BYTEA로 박으면 백업·쿼리·CDN 모두 무거워지고 비용도 빠르게 비싸집니다. 이 프로젝트는 굿즈 사진을 **Cloudflare R2**에 두고, DB(`product_photo.r2_key`)에는 *어디에 있는지*만 보관합니다.

## 핵심 패턴: "DB는 메타, 스토리지는 바이트"

```
┌─────────────────────────┐         ┌──────────────────────────┐
│  Supabase (PostgreSQL)  │         │     Cloudflare R2        │
│  ─────────────────────  │         │  ──────────────────────  │
│  product_photo         │         │  실제 JPEG/PNG 바이너리  │
│   ├─ id                 │         │                          │
│   ├─ product_id         │         │  photos/abc-123.jpg      │
│   ├─ r2_key ─────────── │ ──────▶ │  photos/def-456.jpg      │
│   ├─ alt_text           │         │  photos/xyz-789.jpg      │
│   └─ display_order      │         │   ...                    │
└─────────────────────────┘         └──────────────────────────┘
       메타데이터                         실제 바이트
```

DB는 **포인터만** 보관: `r2_key TEXT` (예: `photos/abc-123.jpg`).
실제 사진은 R2에. 표시할 땐 `r2_key`를 R2/CDN 도메인과 합쳐 URL 생성.

## R2 vs S3 vs Supabase Storage

| | AWS S3 | **Cloudflare R2** | Supabase Storage |
|---|---|---|---|
| **Egress 요금** | GB당 ~$0.09 | **0원 (무료)** ⭐ | 플랜 한도 |
| **저장 요금** | $0.023/GB | $0.015/GB | 플랜 한도 |
| **API** | S3 표준 | S3 호환 | 자체 API + S3 호환 |
| **CDN 통합** | CloudFront 별도 구성 | **Cloudflare CDN 자동** | Supabase CDN 자동 |
| **공개 도메인** | 가능, 설정 필요 | 커스텀 도메인 무료 | 가능 |
| **권한 통합 (RLS)** | 별도 IAM | 별도 (서명 URL) | Supabase RLS와 통합 |

이커머스 사이트의 **결정타는 egress(나가는 트래픽)**. 사용자가 사진 볼 때마다 발생하는 트래픽이라 사진 무거운 사이트는 S3에서 청구서 폭발. R2는 이게 0원.

## 왜 Supabase Storage 대신 R2?

같은 Supabase에서 다 처리하면 편한데(권한 통합·관리 통합), 외부 R2를 고른 이유:

| 항목 | Supabase Storage | R2 |
|---|---|---|
| Egress 한도 | 플랜 한도 안에서 무료, 초과 시 비싸짐 | **무제한 무료** |
| 글로벌 CDN 성능 | Supabase CDN | **Cloudflare 글로벌 엣지** (한·일 빠름) |
| 벤더 종속 | 단일 벤더 의존 | DB와 스토리지 분리 → 갈아끼우기 쉬움 |
| 단점 | — | RLS 통합 약함 (직접 서명 URL 발급 필요) |

## 일반적인 업로드 흐름

```
1) admin이 상품 등록 폼 제출
2) 서버: product row INSERT → id 받음 (또는 클라이언트가 미리 생성한 토큰 사용)
3) 서버: presigned URL 발급 (R2 SDK)
   - PUT 권한, 만료 시간 5분 정도, 키는 photos/{nanoid}.jpg
4) 클라이언트: presigned URL로 R2에 직접 PUT (서버 거치지 않음)
   - 트래픽·메모리 절약. 서버는 토큰만 발급
5) 업로드 끝나면 서버: product_photo INSERT (r2_key 저장)
6) 사용자가 상품 상세 페이지 열면:
   r2_key → CDN URL 조립 → <img src="https://cdn.../photos/...jpg">
```

핵심: **클라이언트가 R2에 직접 업로드.** 서버를 통과시키면 메모리·CPU·시간 낭비.

## r2_key 설계

`r2_key`는 R2 버킷 안에서 unique한 식별자. **PK와 독립적**이라 어떤 토큰을 써도 됨:

```ts
// 옵션 A: nanoid
const r2Key = `photos/${nanoid(12)}.jpg`;

// 옵션 B: UUID v4
const r2Key = `photos/${crypto.randomUUID()}.jpg`;

// 옵션 C: 부모 product 기반
const r2Key = `product/${productId}/${nanoid(8)}-front.jpg`;
```

선택 기준:
- 단순 unique만 필요 → A, B
- 객체를 디렉토리 단위로 묶어 관리하고 싶음 → C

## 보안 / 권한

R2 자체에는 RLS가 없으므로 다음 패턴 중 하나:

| 패턴 | 설명 |
|---|---|
| **공개 버킷 + 추측 불가 키** | 모든 사진을 누구나 볼 수 있음. 키가 nanoid라 nondiscoverable. 카탈로그 사이트에 적합 |
| **비공개 버킷 + presigned GET** | 매 요청마다 서명 URL 발급. 만료 시간으로 통제. 사용자 전용 자료에 적합 |
| **공개 + signed cookies (Cloudflare Access)** | 도메인 단위 통제 |

이 프로젝트는 카탈로그 사이트라 **공개 버킷 + 추측 불가 키**가 자연스러움.

## 이 프로젝트의 결정

`product_photo` 테이블이 R2 키를 보관:

```sql
CREATE TABLE product_photo (
    id            BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id    BIGINT      NOT NULL,
    r2_key        TEXT        NOT NULL,     -- ← 핵심: R2 객체 키
    alt_text      TEXT,
    display_order INT         NOT NULL    DEFAULT 0,
    is_thumbnail  BOOLEAN     NOT NULL    DEFAULT false,
    -- audit 컬럼 ...
);

COMMENT ON COLUMN product_photo.r2_key IS 'Cloudflare R2 객체 키. CDN URL 조립의 베이스';
```

R2 키 포맷은 마이그레이션에서 강제하지 않음 — 운영하면서 결정. 권장:
- prefix: `photos/`
- 본체: nanoid 또는 UUID
- 확장자: 원본 그대로 (`.jpg`, `.png`, `.webp`)

CDN URL 조립은 앱 레이어에서:
```ts
// 예시 (실제 도메인은 환경변수로)
const cdnUrl = (r2Key: string) => `${process.env.R2_PUBLIC_URL}/${r2Key}`;
```

## 알아둘 함정

- **삭제 동기화** — `product_photo` row만 지우면 R2 객체는 남음. 트랜잭션 후 R2 DELETE 호출까지 묶어야 함. 실패 시 정리 cron 또는 weekly cleanup. **단 아래 "주문 스냅샷 참조" 예외를 반드시 적용.**
- **⚠️ 주문 스냅샷 참조 = R2 삭제 제외** — `order_item.product_thumbnail_key`가 주문 시점 썸네일 `r2_key`를 **스냅샷**한다(주문 내역에 *산 그 사진*을 보여주기 위함). 주문은 영구 이력이므로 **R2 객체 삭제·orphan GC는 `order_item`이 참조하는 `r2_key`를 반드시 제외**해야 한다 — 아니면 과거 주문 썸네일이 깨진다. (현재는 R2 삭제 로직 자체가 없어 우연히 안전하나, 삭제를 붙일 때 이 예외를 함께 구현할 것. 키가 `uuidv7`이라 재사용·덮어쓰기가 없어 참조는 항상 유효.)
- **이미지 가공** — 썸네일·WebP 변환 등은 R2 자체 기능 아님. Cloudflare Images 또는 별도 트랜스폼 서비스 필요.
- **CORS** — 클라이언트 직접 PUT 시 R2 버킷에 CORS 설정 필요.
- **R2 키 변경 불가 가정** — 일단 박은 r2_key는 *사실상 immutable*. 이름 바꾸려면 R2 객체 복사 + 키 업데이트 + 원본 삭제. 그래서 처음부터 안정적인 식별자로.
