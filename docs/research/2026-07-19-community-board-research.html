공지·커뮤니티 게시판, 실서비스들은 이렇게 만든다

위버스 · 당근 동네생활 · 네이버 팬카페 · 디시 · 더쿠 · 무신사 · 카페24를 분석한 결과 — 공지는 단방향 문서 목록이 표준이고, 게시판 분류는 유형·대상 2축 프레임으로 수렴하며, 분류 관리 · 거래글 정책 · 위반 처리엔 각각 검증된 모델이 존재한다.

NOTICE

① 공지사항 — 커머스 표준이 이미 존재

서비스구조교훈
카페24·아임웹쇼핑몰 기본 게시판 유형 — admin 작성, 목록+상세, 댓글 없음. FAQ·이용안내와 세트공지 = 단방향 문서 목록. 댓글·상호작용 없는 게 커머스 표준
네이버 팬카페공지 3종 분리: 전체 / 게시판 / 필독 — 필독은 최대 2개 제한고정(pin)은 무제한이면 목록 잠식 — 고정 개수 제한이 검증된 설계
위버스공지가 아티스트 페이지 하위에 묻혀 발견성 문제가 리디자인 대상으로 지적공지는 저장 구조보다 노출 위치(홈 접점)가 성패

BOARD

② 자유게시판 — 팬덤 커뮤니티의 실사용 패턴

서비스구조교훈
위버스피드형, 팬+아티스트 글, 댓글+답글, 좋아요(Cheers)Cheers 랭킹이 "cheer my post" 스팸 유발 — 좋아요·트렌딩은 어뷰징 표면. 댓글·답글은 기본 기대치. 모더레이션 부족이 유저 불만 1순위
네이버 팬카페게시판 세분화 + 말머리 + 글양식 + 등급제 + 스탭 분업대형 운영 모델 — MVP엔 과함. 유형 분류를 "게시판"이라는 무거운 컨테이너로 구현한 사례
무신사커뮤니티 커머스 — 게시판·코디 갤러리(사진 UGC)가 유입·체류 엔진커머스 내 커뮤니티의 존재 이유 = 재방문 트래픽. 사진이 핵심 콘텐츠
더쿠완전 익명("무명의 더쿠" + 글 안 임시 번호)익명 = 활성도↑ 모더레이션 비용 폭증 — 루머·비방 상시화로 운영이 게시판 세분화(격리)로 대응한 실증

댓글 구현 패턴: 깊이 제한(1단 대댓글) 조건에서는 parent_id 자기참조가 표준 (closure table류는 깊은 트리·대규모용 과설계). 댓글 soft delete는 행 보존 + 내용 마스킹("삭제된 댓글입니다") — 대댓글 트리가 안 무너지는 검증된 패턴.

TRADE POLICY

⑤ 커뮤니티 안의 거래 글 — 3가지 모델, 방임은 없다

모델서비스장치전제 조건
채널 분리당근거래는 중고거래 탭 전용, 커뮤니티(동네생활)와 격리. 위반은 신고 기반 제재(경고→3~30일 정지)전용 거래 기능의 존재
인프라 흡수네이버 카페금지 대신 판매자 인증 + 에스크로 + 분쟁조정센터 + 모니터링을 붙여 수용대형 플랫폼 자원
규칙 격리팬카페 · 디시 갤러리양도 전용 게시판 + 정가 이하만(프리미엄 영구 차단) + 비로그인 금지 + 활동량 요건 + 예매내역 인증샷 필수규칙을 집행할 운영진의 상시 노동
거래 글을 지지 장치 없이 방임 허용하는 실사용 사례는 없다. 네이버가 인프라를 붙인 배경 자체가 카페 거래 사기·플랫폼 책임 논란이었고, 더쿠처럼 장치 없는 공간에선 "사기 거르는 법" 자구책 문화가 형성된다.

팬덤 자치 규범이 요구하는 장치(활동량 요건 = 계정 신뢰 게이트, 인증샷 = 보유 증명)는 과거 검토했던 거래 게시판 설계안의 장치(계정 단위 rate limit, inventory 보유 인증)와 동형 — 거래를 "제대로" 받으려면 결국 그 수준의 구현이 필요하다는 재확인.

ENFORCEMENT

⑥ 게시글 위반 정책 — 신고 사유·제재·법적 프레임

서비스위반 사유 분류처리·제재 방식
당근스팸·어뷰징 / 욕설·명예훼손 / 홍보·광고 / 채팅 남용 (+거래 영역: 전문판매업자·금지품목)위반 글 미노출 + 알림으로 사유 통보가 기본 조치. 제재 사다리: 글 미노출 → 경고 → 이용정지 3~30일(누적 기반 — 30일 내 비매너 3회) → 중대 위반(외부 유도 등) 최대 5년
네이버 (카페·블로그)권리침해 계열이 별도 트랙: 명예훼손 / 사생활 / 초상권 / 저작권2트랙 — ① 커뮤니티 운영진의 자체 삭제·제재(강퇴 등) ② 플랫폼 권리보호센터의 게시중단: 신고 접수 → 1~3일 판단 → 30일 임시 게시중단 → 게시자 이의신청(소명·재게시 요청)
위버스가이드라인·금지어 필터·위반 제재의 존재는 확인되나 본문 접근 불가(SPA) — 세부 기준 미검증

위반 판단은 누가·어떻게 하나 — 감지 계층 사다리. 어느 서비스도 자동만으로 판단하지 않는다. 자동(확실한 것)과 인력(애매한 것)의 하이브리드가 표준이다.

계층방식실례
① 사전 필터 (작성 시점)금칙어·워드필터 — 값싸지만 야민정음·기호 삽입으로 우회 쉬움디시 등 다수 커뮤니티. 네이버는 작성 중 부적절 표현 감지 시 "수정 권고 팝업"으로 진화 중
② 자동 감지 (게시 후)ML이 글을 분류해 확실한 위반은 자동 처리, 애매하면 운영자 검수 큐로 라우팅 (당근의 3단 구조 — Google Cloud 공식 사례)당근: TensorFlow 모델로 금지물품·불법광고 분류, 최근엔 AI가 글+채팅+기기정보를 종합해 사기 가능성 판단. 네이버 클린봇: 문장 맥락 분석 → 감지 시 자동 숨김(2024 카페 댓글까지 확대)
③ 신고 (유저)자동이 못 잡는 것의 발견 채널 — 크라우드소싱전 서비스 공통. 당근 AI도 "신생아 판매글"을 못 걸러낸 보도 사례가 있음 — 자동 판단 한계의 실증, 신고·인력이 최종 백스톱
④ 인력 심사 (최종 판단)애매 케이스·신고 건·권리침해류의 최종 판정당근 운영자 검수 큐 · 네이버 권리보호센터(1~3일 판단)

별개 축으로 유저 개인 필터(디시의 단어·ID·IP 차단 설정)도 있다 — 플랫폼의 판단이 아니라 개인의 큐레이션으로, 판단 부담을 유저에게 분산하는 장치.

법적 프레임 — 정보통신망법 임시조치(제44조의2): 권리침해(명예훼손 등) 주장자가 침해사실을 소명해 삭제를 요청하면, 판단이 어렵거나 다툼이 예상될 때 30일 이내 접근 임시차단을 할 수 있고, 조치 사실을 게시판에 공시해야 한다. 임시조치는 삭제가 아니라 비공개(원본 보존)다 — 게시판 운영자가 갖춰야 할 실무 수단은 "보존형 숨김 + 사유 통보 + 신고 접수 창구"로 요약된다.

우리 설계 함의: ① 숨김 스탬프(hidden_at, 삭제 아닌 보존) 축은 당근 미노출 선례와 같은 결이며, 권리침해 신고 처리에 필요한 기록의 일부 기술적 기반이 된다(법적 임시조치 절차의 충족 여부는 별도 운영 절차와 함께 검토). ② 신고 사유 세트는 당근 실례를 근거로 스팸·광고 / 욕설·비방 / 개인정보 노출 / 거래글(정책 확정 시) / 기타 계열로 설계한다. ③ 계정 단위 제재 사다리(경고→기간 정지)는 누적 데이터가 쌓인 뒤의 후속 — v1은 글 단위 조치(숨김)와 처리 기록까지만. ④ 이의신청 절차는 v1에선 문의 채널로 갈음하고 공식 기능은 후속. ⑤ v1의 판단 주체 = 신고(발견) + admin 심사(판단) — 업계 하이브리드 사다리에서 자동 계층(①②)만 뺀 형태다. 금칙어 사전 필터는 저비용이지만 우회가 쉬워 후속 저순위, ML 감지는 규모가 생긴 뒤의 원거리 후속.

DATA MODEL

⑦ 공지 ↔ 게시판 — 테이블 분리 vs 유형 컬럼

시스템구조맥락 · 대가
WordPress단일 wp_posts + post_type (글·페이지·첨부·리비전·메뉴까지)유형별 전용 필드가 wp_postmeta(EAV)로 밀려나 글 하나에 메타 20~50행 — 규모에서 쿼리·검색 성능 저하. 커뮤니티 표준 조언: "구조가 크게 다르고 양이 많으면 별도 테이블"
phpBB · Discourse단일 테이블 + topic_type(Normal/Sticky/Announcement/Global) 또는 pinned 플래그이들의 "공지"는 게시판 안 고정 글 — 일반 글과 완전 동질(같은 필드·댓글·작성 흐름)이라 플래그로 충분
XE(라이믹스)모든 게시판이 documents 단일 테이블 (모듈 구분)한국 양대 솔루션이 정반대 전략 — 둘 다 "동질 게시판의 멀티 인스턴스" 문제이지, 공지/게시판 같은 이질 도메인 분리 문제가 아님
그누보드게시판마다 테이블 분리 생성(g5_write_{board})

모델링 이론(STI vs 분리) — 단일 테이블 상속은 유형 간 공유 속성이 많고 동작이 유사할 때 적합. 공유가 적으면 nullable 스프롤 + 유형별 NOT NULL 불가로 unwieldy해진다는 것이 교과서적 판정 기준이며, 공통 권고는 "의심되면 단순·명료한 쪽".

판정 기준 = "공지가 게시글과 동질인가." 우리 공지는 이질(작성 admin 전용 · 댓글 없음 · 카테고리·고정 · 홈 노출)이고 공유 필드는 제목·본문뿐, 자식 테이블(댓글·사진·신고)은 전부 게시판 전용 — 이론·실증 모두 분리 테이블(notices ↔ posts)을 가리킨다. 단일화의 유일한 이득(댓글·신고 인프라 공유)은 댓글 없는 공지엔 해당 없음.

확장 경로: 훗날 자유게시판이 여러 개가 되면 그건 동질 인스턴스 문제 — board 마스터 + post.board_id를 게시판 도메인 안에서 도입한다(그누보드·카페24 경로, 공지와의 분리는 유지).

DECISIONS

⑧ 현재까지의 결정 현황
