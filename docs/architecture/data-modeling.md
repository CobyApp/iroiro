# 데이터 모델링 (DB 스키마 작성 규칙)

> **DB 테이블·컬럼을 어떻게 설계하고 명명하는가**의 단일 진실.
> 스키마를 새로 만들거나 바꾸기 전 매번 통과한다. (운영·접근 규칙은 [auth-and-data.md](./auth-and-data.md))

이 문서는 스키마 작업을 진행하며 규칙을 ✅ 예시 / ❌ 반례 쌍으로 적립하는 **살아있는 문서**다. 빈 항목은 아직 확정 전이다.

| GRANT 매트릭스·`app` 롤, 세션, 스토리지, `db/schema.sql` 적용 절차 등 **운영** | [auth-and-data.md](./auth-and-data.md) |

## 규칙 (작업하며 적립)

> 각 항목은 스키마 수정 작업 중 확정되는 대로 ✅ 예시 / ❌ 반례 쌍으로 채운다.
> 항목 자체도 작업하며 추가·재배치할 수 있다 (이 목록은 출발점일 뿐 확정된 분류가 아니다).

### 네이밍 (테이블·컬럼·제약·인덱스)

#### ✅ 규칙
- **테이블: snake_case 단수** (`team`, `member`, `product`, `account`, `order`, `cart_item`, `order_item`). 복수형 금지.
- **SQL 예약어 충돌**(예: `order`)은 단수를 유지하고 raw SQL에서 **항상 큰따옴표**(`"order"`)로 쓴다. Prisma는 `@@map("order")`로 자동 처리하므로 모델 코드에는 영향 없다.
- **컬럼: snake_case** (DB) ↔ **camelCase + `@map`** (Prisma).
- **인덱스: `<테이블>_<컬럼…>_idx`**, 고유: `<테이블>_<…>_unique`(또는 `_uq`), CHECK 제약: `<테이블>_<의미>` (예: `order_amounts_non_negative`, `cart_item_quantity_positive`).

#### ❌ 반례
- 복수 테이블명(`orders`, `products`)
- 예약어 회피용 접두/복수 변형(`tbl_order`, `orders`)
- 인덱스명 자동생성에 의존(`db/schema.sql`·Prisma 중 한쪽이라도 `map` 이름 누락)

### 기본 키 / 식별자

#### ✅ 규칙
- **기본 PK**: `id BIGINT GENERATED BY DEFAULT AS IDENTITY` (Prisma `BigInt @id @default(autoincrement())`).
- **회원성·포터블 식별이 필요한 데이터**: `UUID`(앱 생성 UUIDv7, DB default 없음) — `account` 선례.
- **사람이 읽는 외부 식별자**(주문번호 등)는 PK와 **별도 비즈니스 키 컬럼**(`order_no TEXT`, unique)으로 분리한다. IDENTITY PK를 URL·외부에 직접 노출하지 않는다(열거 노출 방지).

#### ❌ 반례
- 자연키를 PK로 사용
- 외부 노출 식별자를 IDENTITY PK 하나로 겸용
- 비즈니스 키(`order_no`)에 unique 인덱스 누락

### 타임스탬프 / 감사 컬럼

#### ✅ 규칙
- **mutable 테이블**: `created_at`, `updated_at` `TIMESTAMPTZ NOT NULL DEFAULT now()` + 각각 단일 인덱스.
- **append-only / 불변 스냅샷 테이블**: `created_at`만 두고 `updated_at`은 생략 — `order_item`, `order_status_history` 선례.
- **`created_by` / `updated_by`(TEXT)**: **관리자 관리(catalog) 테이블에만** 둔다. 회원 소유(user-owned)·PII 테이블은 생략하고 소유자는 `account_id`로 표현 — `account`/`order` 선례.

#### ❌ 반례
- 불변 스냅샷 테이블에 `updated_at` 추가
- user-owned 테이블에 `created_by`/`updated_by`를 무분별하게 추가

### 타입 선택 (금액·통화·열거형·텍스트 등)

#### ✅ 규칙
- **금액: `INT`(원 단위 정수)**. 소수점 없음. 음수 불가 컬럼엔 `CHECK (… >= 0)`, 수량엔 `CHECK (… > 0)` (이 CHECK를 *왜·어느 레이어에* 두는지는 [제약 레이어링] 절).
- **비율/환율: `NUMERIC(p, s)`** (예: 환율 `NUMERIC(8,4)`).
- **열거형: `TEXT` + 앱(zod) 검증**. DB `CREATE TYPE … AS ENUM` 미사용(마이그레이션·이식 유연성).
- **가변 구조/외부 응답: `JSONB`** (예: `payment.raw_response`, `name_i18n`).
- **식별자**: 내부 PK/관계는 `BIGINT`, 회원은 `UUID`, 비즈니스 키/토큰은 `TEXT`.
- **정렬 순서 컬럼(`display_order`): 값을 만드는 주체로 시작값을 정한다.**
  - **기계(앱 배열 index)가 만들면 0부터** + `INT NOT NULL DEFAULT 0`. 선례: `product_photo`·`post_photo`·`notice_photo` — 전부 `displayOrder: index`로 채운다. 0-based여야 읽고 쓸 때마다 ±1 변환이 생기지 않고, `DEFAULT 0`도 이 경우에만 정합한다(1-based라면 기본값 행이 1번보다 앞에 선다).
  - **사람이 입력하면 1부터** + zod `.positive()`. 선례: `team_member.display_order`(관리자가 "팀 내 정렬 순서"를 직접 입력). 관리자에게 "첫 번째 = 0"은 직관에 어긋나고, 정렬은 상대 비교라 1부터 받아도 동작이 같다.
  - 사람에게 숫자를 **보여줄 때만** 변환한다(선례: 상품 사진 zip 파일명이 `displayOrder + 1`로 `01`, `02`…).
  - 근거: 커뮤니티 관례가 이 축으로 갈린다 — Rails `acts_as_list`는 `top_of_list` 기본 1이고 0을 "배열 인덱싱처럼 쓸 때의 옵션"으로 두는 반면, WordPress `menu_order`·.NET `ColumnAttribute.Order`는 0-based다(조사: 2026-08-03).

#### ❌ 반례
- 금액을 `float`/소수 `numeric`으로(원 단위인데 부동소수 오차)
- DB enum 타입 사용
- 열거값을 정수 코드로 저장(가독성·이식성 손실)
- 사람이 입력하는 `display_order`를 0부터 받기(관리자 화면에 "첫 번째 = 0"이 노출됨)
- 같은 이름의 `display_order`가 테이블마다 다른 시작값 규칙을 쓰는데 근거가 없기

### 외래 키 / 관계 / 삭제 정책

**결정: DB 레벨 FK 제약(`REFERENCES`)을 두지 않는다.** 관계는 `<참조테이블 단수>_id` 컬럼으로 표현하고, 참조 무결성은 **애플리케이션 레이어**에서 관리한다. 결정 배경(확장성·성능·마이그레이션)은 [../lessons/05-foreign-keys.md](../lessons/05-foreign-keys.md)에 기록.

> 트레이드오프(인지하고 채택): FK를 빼면 (1) orphan을 DB가 막아주지 않고, (2) DB 도구의 관계 자동 탐색을 잃으며, (3) Prisma 기본 권장(`relationMode="foreignKeys"`)에서 벗어난다. 아래 대체 장치로 상쇄하는 것을 **규칙으로 강제**한다.

#### ✅ 규칙 (FK 없이 관계·무결성을 유지하는 법)
- **관계 컬럼 네이밍**: `<참조테이블 단수>_id` (예: `order_id`, `product_id`). `REFERENCES` 제약은 걸지 않는다.
- **인덱스 수동 필수**: FK가 없으면 인덱스가 자동 생성되지 않는다. 모든 관계 컬럼에 `CREATE INDEX`를 **직접** 건다 — 빠지면 join·필터가 풀 스캔이 된다.
- **Prisma는 `relationMode = "prisma"`**: 관계는 모델에 유지하되 DB FK를 만들지 않는다. 자동 인덱스가 없으므로 관계 스칼라 필드에 `@@index`를 명시한다.
- **쓰기 검증은 Server Action에서**: 자식 INSERT 전 부모 존재를 확인한다. 삭제는 앱 레벨 cascade로 자식을 먼저 정리한다 (DB `ON DELETE`가 없으므로).
- **관계 조회**: 도메인 내부 관계는 Prisma `@relation` + `include`로, 교차 도메인 참조는 명시적 다중 쿼리 후 앱에서 조합한다(`relationMode="prisma"`라 조인은 Prisma가 앱 레벨에서 수행).
- **orphan 점검**: 고아 행 탐지 쿼리를 두고 정기적으로 확인한다.

#### ❌ 반례
- `*_id` 컬럼에 인덱스 누락 → FK가 없으니 자동으로 안 생긴다.
- 부모 존재 확인 없이 자식 INSERT → 검증 주체가 사라져 무결성이 깨진다.
- `REFERENCES` / `FOREIGN KEY` 제약 추가 → 이 프로젝트의 FK 미사용 결정에 어긋난다.
- Prisma `relationMode`를 `foreignKeys`(기본)로 두기 → DB에 FK가 생성된다.

### 제약 레이어링 (DB 제약 vs 애플리케이션 검증)

**결정: 규칙을 "변동하는 비즈니스 정책"과 "불변 도메인 불변식"으로 나눈다. 정책은 앱에만, 불변식은 앱 검증 + DB 제약 백스톱(둘 다)으로 둔다.** 판단 기준 한 줄: *"이 규칙은 비즈니스 사정으로 바뀌나, 아니면 데이터의 의미가 바뀔 때만 바뀌나?"*

> 업계에서 널리 권장되는 패턴도 "DB냐 앱이냐"의 택일이 아니라 *서로 다른 목적의 하이브리드*다 — 앱은 UX·가시성, DB는 출처(직접 SQL·다른 경로·동시성)와 무관한 무결성. 두 레이어의 중복은 정상이며 낭비가 아니다 (근거 출처는 절 끝 참고).

#### ✅ 규칙
- **변동하는 비즈니스 정책 → 앱(zod/Server Action)에만.** 무료배송 임계액·구매 한도·할인율처럼 비즈니스 사정으로 달라지는 규칙. DB 제약으로 박으면 정책 변경마다 마이그레이션이라 오히려 손해.
- **절대적 단일 행 도메인 불변식 → 앱 검증 + DB 제약(CHECK/NOT NULL) 백스톱.** 음수 불가 금액·수량, 금액 합계 공식, 필수값 등 *데이터의 의미가 안 바뀌면 불변*인 규칙. 앱 검증(zod·원자적 `WHERE` 조건)은 UX·가시성용 1차 표현, DB 제약은 우회 불가능한 최후 방어선. 구체 CHECK 예시·네이밍은 [타입 선택]·[네이밍] 절 참조.
- **참조 무결성(FK)은 불변식이라도 예외 → 앱.** FK도 넓게는 불변식이지만 쓰기당 룩업 비용·결합·샤딩·마이그레이션 마찰 때문에 앱으로 민다 ([외래 키 / 관계 / 삭제 정책] 절). 즉 *값싼 단일 행 불변식*(CHECK/NOT NULL)과 *관계형 제약*(FK)을 다르게 취급한다.

#### 근거 (왜 불변식은 DB 백스톱까지 두는가)
- **앱 단독 검증은 무결성에 불충분하다.** 직접 SQL·다른 서비스·스크립트·리팩터링·동시성으로 우회·유실될 수 있다("constraints are law; application logic is advice"). 동시성 예: 재고 차감 read-check-write는 조건을 단일 UPDATE의 `WHERE`에 넣어야 음수 유실이 없고, CHECK는 그 위 백스톱이다.
- **데이터는 코드보다 오래 살고 덜 바뀐다.** 스키마 정합에 들인 시간의 ROI가 크다(= last line of defense). 절대 불변식엔 DB의 경직성이 *마찰이 아니라 보호*다(의도된 마이그레이션 없이는 못 깨진다).
- **정상 쓰기 오버헤드 ≈ 0 (측정 확인).** NOT NULL은 널 비트맵 1비트 검사라 사실상 무료(PG 공식문서상 `CHECK(col IS NOT NULL)`보다 효율적). 단순 스칼라 CHECK도 최악치가 합성 INSERT 벤치마크에서 **~5%**(narrow 테이블·2.56M행)일 뿐, 실제 앱에선 WAL·인덱스·네트워크 비용에 묻힌다. **읽기엔 비용 없음**(쓰기 경로 한정). 측정상 유의미한 쓰기 비용은 FK(부모 룩업+잠금)·UNIQUE(인덱스 유지)에서 나오며, 이 프로젝트는 그중 FK를 안 쓴다.

#### 운영 (변경·대용량에서의 용이성)
- **제거·완화**: `DROP CONSTRAINT`는 카탈로그만 바꾸는 즉시 연산(스캔·재작성 없음, 데이터 양 무관). 짧은 ACCESS EXCLUSIVE 락만 `lock_timeout`으로 관리.
- **추가·강화(대용량)**: 인라인 `ADD CONSTRAINT`는 검증 스캔 동안 **ACCESS EXCLUSIVE 락**으로 모든 읽기·쓰기를 막는다(추가 시점의 유일한 실비용). 그래서 `ADD CONSTRAINT … NOT VALID`(신규 쓰기 즉시 적용, 기존 행 스캔 생략, 짧은 락) → `VALIDATE CONSTRAINT`(SHARE UPDATE EXCLUSIVE라 DML 안 막음) 2단계로 분리해 거의 무중단으로 만든다.
- **기존 데이터 정리**: 위반 데이터 청소 비용은 제약을 DB·앱 어디 두든 동일하다. 오히려 처음부터 CHECK가 있으면 위반 행이 애초에 안 쌓여 미래 마이그레이션 부담이 *줄어든다*.

#### 가시성 (DB 제약이 코드에 안 드러나는 우려 해소)
- **제약에 의미 있는 이름**을 붙인다(`product_stock_non_negative`) → 위반 에러 메시지에 규칙명이 드러난다.
- **CHECK 위반(SQLSTATE `23514`)을 DAL에서 도메인 에러로 매핑**한다 — unique 위반을 처리하는 기존 `runWithUniqueCodeGuard`와 동일 패턴. 제약이 TS 코드에서 참조되어 발견성이 생긴다.
- 불변식의 1차 표현(zod)을 앱에 유지하므로 신규 입사자는 코드에서 규칙을 먼저 본다.

#### 이식성 (DBMS 호환)
- **핵심 제약(CHECK/NOT NULL/UNIQUE/FK)은 ANSI SQL 표준** → 어느 관계형 DBMS로도 이식 가능. 불변식 백스톱 철학 자체는 Postgres 전용이 아니다.
- **"지원"과 "강제"는 다르다 (버전까지 확인)**: MySQL은 8.0.16+부터만 `CHECK`를 강제(이전 버전은 파싱만 하고 무시), MariaDB는 10.2+. FK는 MySQL InnoDB·SQLite `PRAGMA foreign_keys=ON`에서만 강제된다.
- **이 프로젝트의 최대 Postgres(계열) 종속점은 부분 인덱스**(`CREATE UNIQUE INDEX … WHERE …`, 예: 썸네일·승인결제 unique). PostgreSQL·SQL Server·SQLite는 되지만 **MySQL은 미지원**(생성 컬럼으로 우회).
- **운영 문법·에러코드는 Postgres 기준**: 위 운영 절의 `NOT VALID`/`VALIDATE CONSTRAINT` 문법, 가시성 절의 `SQLSTATE 23514`(check_violation) 값은 Postgres 고유다. 엔진 교체 시 대체 필요(개념 등가물: Oracle `ENABLE NOVALIDATE`, SQL Server `WITH NOCHECK`; MySQL은 일반 코드 `23000`+자체 에러번호).
- **원자적 조건부 UPDATE 기법은 모든 트랜잭션 DBMS에서 안전**. 단 정확한 메커니즘(PG의 READ COMMITTED 재평가)·기본 격리수준(MySQL InnoDB는 REPEATABLE READ)만 엔진별로 다르다.

#### ❌ 반례
- 변동 정책(할인율·배송 임계액)을 DB 제약·트리거로 박기 → 정책 변경마다 마이그레이션.
- 절대 불변식(음수 금지 등)을 앱 검증에만 의존 → 우회 경로·리팩터링·동시성으로 음수 데이터가 조용히 유입.
- "앱에서 검증하니 DB 제약은 불필요"라며 백스톱 생략 → NOT NULL을 앱에서만 보장하는 것과 같은 안티패턴.
- 대용량 테이블에 `NOT VALID` 없이 `ADD CONSTRAINT … CHECK` → 검증 스캔 동안 ACCESS EXCLUSIVE 락으로 장시간 블로킹.

### DDL 작성 구조 — 스키마/제약/인덱스 분리 (테이블 블록형)

> 제약을 *어느 레이어*에 둘지는 [제약 레이어링] 절. 여기서는 DB에 두기로 한 제약·인덱스를 *`db/schema.sql`에 어떻게 배치*하는가를 정한다.

#### ✅ 규칙
- **`CREATE TABLE`은 "구조"만**: 컬럼·타입·`NOT NULL`·`DEFAULT`·`PRIMARY KEY`. PK는 행 정체성이라 인라인 유지.
- **`CHECK`·FK는 `CREATE TABLE` 밖으로**: 테이블 바로 뒤 `ALTER TABLE … ADD CONSTRAINT …`로 분리한다. 여러 개면 한 `ALTER`에 콤마로 묶는다. (CHECK는 독립 생성문이 없어 `ALTER`가 유일한 분리 수단 — `CREATE CONSTRAINT`는 존재하지 않음.)
- **`UNIQUE`/인덱스는 `CREATE [UNIQUE] INDEX`로 분리**: partial(`WHERE …`)이 필요해 인덱스 형태가 강제되며, 평범한 UNIQUE도 같은 스타일로 통일한다.
- **블록 순서**: 테이블마다 `CREATE TABLE → ALTER ADD CONSTRAINT(CHECK) → CREATE INDEX → COMMENT`를 한 블록으로 묶고, `REVOKE`/`GRANT … TO app`은 해당 도메인 섹션 끝에 모은다(`db/schema.sql`의 `[init_*]` 섹션 선례). 새 테이블에 GRANT를 빠뜨리면 `app` 롤이 `permission denied`.
- **비용**: 빈 신규 테이블엔 인라인이든 분리든 생성·런타임 비용이 동일하다(순수 가독성 선택). 대용량 테이블 *후속* 변경의 락·스캔 주의는 [제약 레이어링]의 운영 절 참조.

#### ❌ 반례
- `CREATE TABLE` 안에 `CHECK`/`UNIQUE`를 인라인으로 남김(구조와 제약 혼재)
- PK·`NOT NULL`까지 `ALTER`로 빼서 구조 정의를 흩뜨림(과분리)
- 한 테이블의 인덱스를 파일 전역에 흩어 놓아 블록 응집을 깨뜨림
- 테이블만 추가하고 도메인 섹션의 `GRANT … TO app`을 빠뜨림

### 인덱스

#### ✅ 규칙
- **시간 정렬·증분 연동용 인덱스**: `created_at`, `updated_at` 컬럼이 있는 일반 mutable 테이블은 각각 단일 인덱스를 둔다.
  - 예: `CREATE INDEX account_created_at_idx ON account (created_at);`
  - 예: `CREATE INDEX account_updated_at_idx ON account (updated_at);`
- **정렬 방향은 기본 생략**: 단일 방향 정렬은 B-tree 역방향 스캔으로 처리할 수 있으므로 `ASC`/`DESC`를 고정하지 않는다. 혼합 정렬·NULL 정렬 등 명확한 요구가 있을 때만 방향을 지정한다.
- **Prisma 정합성**: `db/schema.sql`에 추가한 인덱스는 `prisma/schema.prisma`에도 같은 이름의 `@@index`로 반영한다(`npm run db:pull` 후 확인).
- **복합 커서 인덱스는 요구 발생 시 승격**: `(updated_at, id)` 같은 복합 인덱스는 실제 커서 페이지네이션·증분 연동 요구가 생기면 기존 단일 인덱스를 대체한다.
- **의미별 시간 컬럼 존중**: 이력·만료·동기화처럼 목적별 시간 컬럼이 있다면, 컬럼명에 고정하지 말고 실제 조회 기준 컬럼에 인덱스를 둔다.

#### ❌ 반례
- `created_at` / `updated_at` 정렬 조회가 많은 테이블에 시간 인덱스 누락
- 명확한 요구 없이 시간 인덱스 방향을 `ASC`/`DESC`로 고정
- 아직 필요하지 않은 `(created_at, id)` / `(updated_at, id)` 복합 인덱스를 선제 추가
- `db/schema.sql`에는 인덱스를 추가했지만 Prisma schema에는 누락
- 더 명확한 목적별 시간 기준 컬럼이 있는데 무조건 `created_at`만 인덱싱

### Prisma schema ↔ `db/schema.sql` 정합성

#### ✅ 규칙
- **`db/schema.sql`이 단일 진실**. Prisma는 introspect(`npm run db:pull`) 후 camelCase 매핑을 수동 유지(파일 상단 주석 참조). 절차: `db/schema.sql` 편집 → `npm run db:reset` → `npm run db:pull && npm run db:generate`.
- **인덱스/유니크/partial은 양쪽에 같은 `map` 이름으로 반영**. partial은 Prisma에서 `where: raw("(…)")`.
- **관계는 도메인 *내부*만 `@relation` 선언**(`relationMode="prisma"`라 DB FK는 안 생김). **교차 도메인 참조**(예: `account_id`, `product_id`)는 `@relation` 없이 bare 스칼라 + `@@index`로 둔다 — `product_photo` 선례.
- **소유키(`account_id`)를 자식마다 비정규화하지 않는다** — 소유권은 부모(`order_id`)로 도출한다. **경계 데이터**(PII·결제: `order_address`·`payment` 등) 테이블에 한해 `account_id`를 두어 앱 DAL의 소유권 필터(`WHERE account_id = 세션`)를 단순하게 한다. 그 외 자식은 스키마를 도메인-순수로 유지한다 — `order_item`·`order_status_history` 선례.
- **변경 후 `prisma validate`로 정합성 확인** 후 커밋.

#### ❌ 반례
- `db/schema.sql`에만 또는 Prisma에만 인덱스가 존재(한쪽 누락)
- `prisma/schema.prisma`를 직접 고치고 `db/schema.sql`은 두기(다음 `db:pull`에서 사라진다)
- `map` 이름 불일치(introspect가 임의 이름을 부여하게 됨)
- 교차 도메인까지 `@relation` 강제(모델 결합도 상승, back-relation 강제로 기존 모델 수정 유발)
