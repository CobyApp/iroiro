# 커밋 메시지 정책

이 문서는 커밋 메시지 형식의 단일 원천이다.

git 안전 절차, stage 범위, 커밋 분할, hook 실행 방식은 각 실행 환경의 어댑터가 담당한다. 메시지 형식 자체는 이 문서를 따른다.

## 템플릿

```text
<type>: <한국어 제목 (70자 미만)>

- <선택: 본문 bullet - "왜"에 집중>
- <bullet 2>
- <bullet 3 (필요 시)>
```

본문이 있으면 모든 줄이 `-`로 시작하는 bullet 형식이어야 한다. 산문 문단은 금지한다.

## type 선택

| type | 언제 쓰는가 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 빌드, 의존성, 설정 |
| `test` | 테스트 추가/수정 |
| `style` | 포맷팅 |
| `perf` | 성능 개선 |
| `ci` | CI 설정 |
| `revert` | 이전 커밋 되돌리기 |

판단 기준:

- 새 기능이면 `feat`
- 결함 수정이면 `fix`
- 동작 변화가 없으면 `refactor`, `style`, `docs`, `chore` 중 선택
- 단순 버전 업이나 도구 설정이면 보통 `chore`

## 제목 룰

- 한국어로 작성한다. 영문 제목은 쓰지 않는다.
- 70자 미만으로 작성한다.
- 명사형 또는 명령형으로 쓴다. 과거형과 마침표는 쓰지 않는다.
- `<type>: ` 뒤에는 공백 한 칸을 둔다.
- `Co-Authored-By:` footer는 쓰지 않는다.

| 좋은 예 | 나쁜 예 |
|---|---|
| `docs: MVP 기술 스택 및 아키텍처 결정 문서 추가` | `Added new docs` |
| `feat: 상품 상세 페이지 R2 이미지 업로드 추가` | `feat: 추가했음.` |
| `refactor: modules/admin 가드 layout으로 통합` | `Refactor: ...` |

## 본문 룰

작업 의도가 자명하면 본문은 생략한다. 의도가 비자명하면 본문을 추가하되, 모든 줄은 `-` bullet로 시작한다.

- 각 줄은 `-` bullet로 시작한다.
- bullet 개수는 보통 1-4개로 제한한다.
- "무엇"보다 "왜"를 적는다.
- 한 bullet이 길면 70자 근처에서 줄바꿈하고, 다음 줄은 `-` 다음 공백 자리에 맞춰 들여쓴다.
- 제목과 본문 사이에는 빈 줄을 1개 둔다.

좋은 예:

```text
docs: MVP 기술 스택 및 아키텍처 결정 문서 추가

- 호스팅, 이미지, DB/Auth, 관리자 페이지 선택 근거 정리
- 영역별 후보 비교와 비용 구조, 분리/확장 시점 기준 포함
```

나쁜 예:

```text
docs: MVP 기술 스택 및 아키텍처 결정 문서 추가

호스팅은 Vercel을 선택했고 이미지는 Cloudflare R2, DB와 Auth는
Supabase를 사용한다. 비용 구조와 분리 시점 기준도 함께 정리.
```

## 분할 vs 한 묶음

- 한 의도면 한 커밋으로 묶는다.
- 서로 다른 type이 섞이면 분할한다.
- 너무 작게 쪼개도 히스토리 노이즈가 되므로 한 PR/한 의도를 기본 단위로 본다.
- 판단이 애매하면 묶지 말고 분리하는 쪽이 안전하다.

## 커밋 요청 시 절차

사용자가 명시적으로 커밋을 요청했을 때만 커밋한다.

1. `git status`로 staged, unstaged, untracked 변경을 확인한다.
2. 필요하면 `git diff`로 내용을 확인한다.
3. 변경을 의도/type별로 그룹핑한다.
4. 그룹이 여러 개면 분할안을 사용자에게 먼저 제시하고 동의를 받는다.
5. 그룹별로 `git add <구체적 파일>`을 사용한다. `git add -A`와 `git add .`는 쓰지 않는다.
6. 그룹별로 이 문서 형식에 맞춰 커밋한다.
7. 마지막에 `git status`와 `git log --oneline -5`로 결과를 확인한다.
